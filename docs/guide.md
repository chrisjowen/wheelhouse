# Using Wheelhouse

Everything Wheelhouse does, page by page, and how it runs Firstmate. For the short version, see the [README](../README.md).

## Requirements

- Node.js 22 or newer, and npm.
- A Firstmate checkout and its operational home (the directory with `state/` and `data/`). Wheelhouse starts Firstmate's session there when none is running (see [The Firstmate session](#the-firstmate-session)); it never stops or reconfigures Firstmate.
- Whatever Firstmate's own scripts need (bash, python3, git).
- Optional: the GitHub CLI (`gh`), used to read a pull request's state and checks when Firstmate has no cached observation of it, and by the GitHub checks a [passage file](passages.md) declares.
- `tmux` and Claude Code (`claude`) on your `PATH`, to run and talk to Firstmate from Wheelhouse. Without them Wheelhouse says so, still shows a Firstmate session running elsewhere (read-only), and the rest works as usual.

## Use

Run it inside a Firstmate checkout:

```bash
wheelhouse open
```

Or give the paths:

```bash
wheelhouse open --firstmate ~/firstmate --home ~/crew --port 4310
```

| Option                  | Default                                                                                           |
| ----------------------- | ------------------------------------------------------------------------------------------------- |
| `--firstmate <dir>`     | the Firstmate checkout you are in                                                                 |
| `--home <dir>`          | `$FM_HOME`, else the Firstmate directory                                                          |
| `--port <n>`            | `4310`                                                                                            |
| `--state-dir <dir>`     | see below                                                                                         |
| `--config-dir <dir>`    | see [Passage files](passages.md)                                                                  |
| `--tmux-socket <name>`  | `$WHEELHOUSE_TMUX_SOCKET`, else `wheelhouse`; see [The Firstmate session](#the-firstmate-session) |
| `--no-skip-permissions` | start it with `--dangerously-skip-permissions`                                                    |
| `--no-browser`          | open the browser                                                                                  |
| `--review-model <m>`    | `$WHEELHOUSE_REVIEW_MODEL`, else `sonnet`; see [the PR review](#the-pr-review)                    |
| `--review-effort <e>`   | `$WHEELHOUSE_REVIEW_EFFORT`, else `low` (`low`, `medium`, `high`, `xhigh` or `max`)               |

`wheelhouse` with no subcommand does the same as `wheelhouse open`.

`--state-dir` is where Wheelhouse keeps its own records: the inbox messages it sent (request ids, bodies, delivery outcomes, receipts and the receipts cursor), one file per Firstmate home, `firstmate/session-start.json`, which its SessionStart hook writes to name the Firstmate session's transcript, and what the PR review agent wrote, per task and PR version, beside the home's messages (`pr-review/<task>.json`), and the [messaging gateway](#the-messaging-gateway)'s record beside them (`gateway.json`) and its audit log (`gateway/discord.jsonl`), and the files you attach in the chat (`uploads/`, kept seven days; see [The Firstmate session](#the-firstmate-session)). It defaults to `$WHEELHOUSE_STATE_DIR`, else `$XDG_STATE_HOME/wheelhouse`, else `~/.local/state/wheelhouse`, and must be outside the Firstmate home.

Wheelhouse checks that Firstmate's integration scripts declare the contracts it understands, starts its server on `127.0.0.1` only, and opens the browser. It answers only requests addressed to `127.0.0.1`, `localhost` or `[::1]`; any other `Host` gets a 421, which blocks DNS-rebinding pages. Every request that changes anything (sending a message, attaching a file, starting the Firstmate session, typing into it, stopping it, answering its questions) must also carry an `Origin` equal to the page's own `http://<host>` origin and this launch's session token, which Wheelhouse issues only to the pages it serves; anything else gets a 403. If the scripts look incompatible it still starts, says so in the UI and in `/api/health`, and shows what it can. Press Ctrl+C to close Wheelhouse; Firstmate and its crew keep running.

### Keeping Wheelhouse up to date

When Wheelhouse runs from a git clone (the installed `wheelhouse` linked to a checkout, as in [Developing Wheelhouse](development.md)), it can upgrade itself. The arrow-up icon in the header, beside the bell, is its version and updates: it checks the default branch of the clone's `origin` on GitHub when a page asks and the last check is more than six hours old, or at once from **Check now**, and changes nothing but the fetched branch. While Wheelhouse is up to date the icon stays quiet; when the branch has newer commits it becomes an outlined **Update** button, whose menu lists them (with the new version when `package.json` changed, and **Compare on GitHub**), says what a restart would stop, and offers **Upgrade and restart**. That fast-forwards the clone to the new commit, runs `npm ci` and `npm run build`, and restarts Wheelhouse's server through the same watcher that restarts it after a crash, showing each step; the page reconnects by itself and says it upgraded. Firstmate and its crew keep running.

It never resets, stashes, merges or rebases. A clone with local changes to tracked files (it lists them), on another branch or a detached HEAD, or with commits of its own that the default branch lacks is refused with the reason, and nothing is changed; a small amber dot on the icon marks it. The install and build run in the directory the server runs from, so pages may briefly misbehave while an upgrade builds. A failed `npm ci` or build leaves the clone at the new commit with an incomplete build and shows the end of the output; fix it and rebuild (`npm ci && npm run build`) before Wheelhouse restarts, or it restarts from the broken build. Installed from npm, Wheelhouse is not a clone and says so: update it with `npm install -g @chrisjowen/wheelhouse`. Upgrading from a page needs the server to have been started by `wheelhouse open`, which can restart it.

`wheelhouse upgrade` does the same from a terminal: it lists what is new, asks, upgrades with npm's output shown, then restarts every running Wheelhouse that loads plugins from the same directory (asking first when one has a PR review agent or a service launch in progress). `--check` only says whether there is something new; `--yes` upgrades and restarts without asking.

If Wheelhouse's server dies (a crash, or a process killed outright), a small watcher in `wheelhouse open` restarts it on the same port, up to five times within a minute; if it dies again within that minute, Wheelhouse gives up and closes. The watcher is about Wheelhouse only: it never starts, stops or restarts Firstmate or its crew, and a restarted server does not start a Firstmate session (start one from the home page if you need it). Open pages say plainly when they have lost the server, keep trying, and pick up again on their own once it answers, reloading their data when the server was restarted.

## What you see

The menu down the left carries the main sections (Firstmate, Harbour, Projects, Decisions, Logbook, then any plugin's own page, such as **Improvements**), each with an icon, and Decisions with a count of open questions. It folds to its icons (with their names as tooltips) from its **Collapse** button or Cmd/Ctrl+B, and this browser remembers which you chose; on a narrow screen it is left out and the sections sit in the header instead. The header carries whether Firstmate is on watch, the project switcher, Wheelhouse's version and updates (see [Keeping Wheelhouse up to date](#keeping-wheelhouse-up-to-date)), the [ship's bell](#the-ships-bell), **Settings** (the gear: the [messaging gateway](#the-messaging-gateway) and **Plugins**) and the light/dark switch. Each section keeps its own pages in a row of tabs at its top (Harbour's **Under way** and **Completed**, with the **Harbour**, **Passage** and **Radar** views beside them; the Logbook's pages, then **Plugins**, which opens Settings → Plugins). The switcher lists your projects, each with how many things need you: All projects, the ones you pinned, then the most active (waiting on you, under way, latest activity), six in all, then the rest, with a search box that has the keyboard (arrow keys move, Enter picks, Esc closes); choosing a project scopes the page. Projects whose names share a leading part (split on `-`, `_` or `/`) with another project sit under it as a heading, each shown by its own part: `ai-innovations-chat-agent` and `ai-innovations-workflow` read as **chat-agent** and **workflow** under **ai-innovations**, with the full name on hover; one shown on its own reads "ai-innovations › chat-agent", the prefix giving way first. Each project has a two-letter tile from that part (CA, WO) in one of a few quiet colours, so siblings look different. Each row pins or unpins it and renames it: a friendly name, kept in this browser, replaces the shown name everywhere the project is listed and is found by search along with the full name (clear it to go back to the full name).

- **Home** (`/`, the **Firstmate** tab): the conversation with Firstmate, full width, with a rail beside it, **On deck**, on the left by default; the button with two arrows in the chat's bar moves it to the other side, and this browser remembers which. See [The Firstmate session](#the-firstmate-session) for the chat. Under its headline and Claude headroom, the rail shows one list at a time, in tabs that each carry a count (the tab you pick is remembered in this browser): **Under way** (the default), then **Up next**, folded; **Needs you**: a failed step (say, failed checks or a failed deploy) as an urgent card, then pull requests waiting for your review (with their full URLs) and decisions Firstmate is holding for you, in plain words, then **Decided for you**; **Landed** in the last day, then **Where time went today**; and a tab for each plugin card, such as **Harness**. Every card shows its project as a tag (its short or friendly name, as in the project list), what it is doing now (in the checks stage, the same step strip and plain line as on Harbour), a small passage with the current step marked, and a badge for anything wrong, each with an icon and words (Checks failed, Stuck, Not responding, Your review, Your merge, With reviewers, Your call, Run 2 · Building and the like, Firstmate deciding), and has **Open** (the task page) and **Chat about this** (mentions the task in the message box). A pull request you asked to change after it was reported ready starts a new run (the change goes to the worker that opened it while that worker is still live, and Firstmate starts a new session only once it is gone) and shows under Under way (say **Run 2 · Building**) rather than under Waiting on you, until the worker reports it ready again (see [Passage steps](#passage-steps)). The rail can be resized by dragging its edge (its width is remembered in this browser; a double click restores the default); on narrow screens the chat stands alone and a button opens the rail as a sheet. The project switcher scopes the rail.
- **Harbour** (`/harbour`): the full board. A one-line watch report, then **Your move** (captain-held decisions and pull requests waiting for your review, each showing its screenshot count, the reported live preview link and the pull request link), **Waiting on Firstmate** (decisions a worker raised that Firstmate is handling), **Waiting on reviewers** (green pull requests whose review or approval other people owe, so there is nothing for you to do yet), and each project's work as cards. A card names the work (its title without the project prefix), who is doing it (harness, model and worker name) and what they are doing **Now**, in plain words with its age: the latest status line, else the latest line of the worker's console. While the work is in its checks stage (a no-mistakes validation run: rebase, review, tests, docs, lint, push, pull request, CI), a slim strip with one segment per step takes the Now line's place, with one plain line under it, for example "Reviewing the change · 1m 20s · 1 question for Firstmate", "Answer received · fixing review findings, round 2 · 3m" or "All checks passed · CI green". The step under way is drawn solid, a step waiting on Firstmate amber and a failed step red; the line says the same in words. Work under way is led by the worker's live console (a bounded, read-only sample of the last lines, refreshed every 2 seconds, only while the card is on screen; select it to open it in the browser's full screen, where the worker's screen is drawn large enough to fill it, refreshes every second and stays where you scrolled to, and Esc or the close button returns to the page); finished work by its latest screenshot or a picture of the diff. A card with screenshots shows the newest few as small thumbnails of one size that open in the in-page viewer. A card whose worker reported a preview has **Show live preview**, which embeds it in the card with **Open in new tab** and a feedback box (see the task page). A soft pulse on the current step shows a worker that is busy right now, and the card counts the files changed, the questions raised about the work (answered and still open) and the docs and decision records the worker's session referenced, read or changed ("5 docs referenced · 2 changed"; it opens the task's Docs tab). While the automated review has questions for Firstmate, the checks line ("3 questions for Firstmate") and the question count open them in the card: each question in a sentence or two (the whole question opens in place), where in the change it is, whether it is still waiting on Firstmate, and once Firstmate answers, its call on that question (fix it, no change, keep as is) and why. It updates as Firstmate answers; the task's **Conversation** tab shows the same questions in each exchange. A project switcher (`?project=`) scopes the page, and the **Passage** view (`?view=passage`) puts every task on one chart. The **Radar** view (`?view=radar`) is the fleet as it moves: one dot per task in five lanes (Queued, Building, Testing, Pull request, Landed), placed by the task's current passage step (a step a passage file adds sits in the lane of the built-in step before it). A dot pulses while its worker is busy, turns amber when it is waiting on you and red (a diamond) when it is stuck: blocked, failed, out of contact or at a failed step; a hollow dot is idle, a brass ring is with Firstmate. Dots glide to their new lane as the live fleet read changes (over the page's one existing event stream), and the line above the lanes counts them by state. Landed dots stay for a day, fading after the first hour. Hover, focus or tap a dot for its card: the project, the task, its current step, how long it has been in its lane and, once the page has seen it change step, in that step, and what it is doing, with a link to the task. Time in the lane counts from when the page saw the task move there, else from Firstmate's records (when its validation run started, when it landed); a status line or the date the task was filed is not a move, and where nothing says, it shows as unknown. Under reduced motion nothing glides or pulses. An **Under way | Completed** toggle switches the cards between work still in progress (including what needs you) and landed or finished work, newest first (`?view=completed`); **Your move** shows only under Under way. A **Large | Compact | List** toggle sets the layout, remembered in this browser: **Large** is the full cards above; **Compact** keeps only the title, a project tag, the status, the passage strip and the question count; **List** puts one row per task with its project, current step, status, who it is waiting on (you, Firstmate, reviewers, the crew or earlier tasks) and when it last moved, and every column sorts. Each layout keeps the same sections, filters and project grouping.
- **Projects** (`/projects`): every project in Firstmate's project registry, with or without work, as one card each: its description; how many tasks are under way, waiting on you and landed this week; a dot for each open task (it opens the task); its delivery posture in plain words (for example "Product changes run the full checks; internal tooling goes straight to a pull request. Firstmate merges once checks are green."); when anything last happened; and links to its Harbour, its passage and passage editor, any plugin tabs and its repository (from the clone's `origin` remote, GitHub-style remotes only). A **Cards | List** toggle, remembered in this browser, shows the same as one sortable row per project. Picking a project in the switcher opens its Harbour.
- **Task page** (`/tasks/<id>`): full width, in two columns. On the left, pinned while you look around and resizable by dragging its edge as On deck is, the overview: the task's project and crew, its title and state in plain words, what it is doing now, anything waiting on you or Firstmate (while the work waits on your review, its screenshots, live preview link and pull request link come first here), a small passage, a rough time left, **Live preview** and **Ask Firstmate about this** (opens the home page with the task mentioned in the message box), and its pull request, preview, last check and delivery. Under the overview, for work under way, the worker's **Live terminal** (its live console, which folds away), then the task's time: the work-time estimate (the rough time left jumps to it), where the task's time went and the review questions Firstmate decided on it. On the right, tabs (`?tab=`, kept in the link): **Stages** (the default), **Live preview** (while a worker has reported one), **Conversation**, **Checks**, **Docs**, **Screenshots**, a tab for each plugin section, and **Log**; on narrow screens the overview comes first and the tabs follow. **Stages** is the passage as a vertical list: finished stages fold to one line saying what they came to (say "4 files changed" or "Pull request #13 merged"), the current one is open, later ones are faint, and selecting any stage opens or folds it (**Open all** and **Fold all** do every one). An open stage shows the evidence it produced: files changed, the validation run (under Checks: what is happening now, then a short timeline of what each validation step found or changed and how long it took, with the pull request's CI result on the CI step once the PR is up), the pull request and its CI checks, the report and screenshots. Screenshots show as small thumbnails of one size and open in an in-page viewer (Esc closes, the arrow keys step through them), and selecting a changed file shows its diff against the merge base. Status lines show in plain words, with the raw line behind a small **details** disclosure. **Live preview** embeds a reported preview: only a preview on this machine (`127.0.0.1` or `localhost`) is embedded, in a sandboxed frame, after Wheelhouse has checked that it answers; one that does not answer shows **Preview not running**, and one that refuses to be framed says so, with **Open in new tab** either way. The box under it sends your feedback to the task's worker through Firstmate's inbox, as a note about the task (`Re: <task-id>`) that Firstmate passes on (landed work has no worker, so it has no box). **Full screen** (`&full=1`; Esc closes) puts the page on the left and the feedback on the right: everything sent from this preview, with whether Firstmate has it and any reply, and the box to send more. The feedback sits beside the page, so it never covers what you are commenting on, and **Hide comments** gives the page the full width. **Conversation** is the back-and-forth between the worker and Firstmate, oldest first: each question the worker raised (and each time it was stuck), the automated review's questions (each in plain words with where it is in the change, waiting on Firstmate until it answers, then Firstmate's call on it and why), Firstmate's instructions to the worker, and what you sent Firstmate about the task, each saying who asked, who answered and how it ended (answered, still open, read or not yet read by the worker). **Checks** is what each step of the latest validation run found, in plain words, with what each step did: for tests, how many passed and failed, each failed test with the start of its output (select one to see it), and the scenarios the test step drove; for docs, which documentation changed and what the docs step wrote about it. **Docs** lists the decision records and docs the work changed or the worker's session read; each opens as a document in Wheelhouse (`/tasks/<id>/doc?path=`): one readable column on a paper sheet, with its file name, whether the task changed or only read it, a contents list beside it when it has three or more sections, and **Open on GitHub** when the project is there. **Log** has the ship's log (history from Firstmate's fleet ledger) and the raw terminal output, which is read-only and sampled only while it is open and the Log tab is showing; **Full screen** opens it filling the screen, as on a card.
- **Documents** (`/files?path=`): a Markdown file Firstmate or a worker names, read in Wheelhouse. Wherever Wheelhouse shows their words (chat replies, decision cards and hold reasons, a task's status, notes and report, and the raw line behind **details**), a Markdown file path such as `data/<id>/report.md` is a link to it, and where a status is shown in plain words the files it names that the plain words leave out are listed under it. A relative path is read against the Firstmate home; an absolute one only when it is inside the Firstmate home, Firstmate's own folder, or a live task's project or worktree, and anything else (a `..` or a symlink leading out included) is refused with the reason. The document opens on the same paper sheet as a task's docs, read-only: raw HTML in it never runs (styles, forms, frames and scripts are dropped), and its links and images resolve against its own folder, opening other documents in the reader and images or text files from the same allowed folders.
- **PR review** (`/tasks/<id>/review`, from **Review the pull request** on the task page, **Review PR** on every Harbour card with a pull request, and **Guided review** where a PR waits for your review): the task's pull request as a diff, with a guide on top. **Prepare the guide** asks the review agent (see [The PR review](#the-pr-review)) to read the change with the task's records and put the important hunks first (behaviour changes, risky areas, public APIs) under **Read these first**, numbered in reading order. Each says what it does and **why it was done this way**, from the records, with the records it rests on named (the brief's intent and spec, a commit, a review finding and Firstmate's call on it, the PR description, the worker's questions); when nothing records a reason it says **No recorded reason.**, and the agent's own reading is marked **Why: not recorded**. Routine hunks follow, folded; lockfiles, generated files, snapshots, binaries and formatting-only hunks are folded away under **Boilerplate**. Beside it, and staying beside the diff as you scroll on wide screens, **Ask about this pull request**, and under every hunk **Ask, review or request a change here**: ask the agent a question, or **Request review** for a focused review, and the answer streams in where you asked. **Ask Firstmate for a change** sends a note about the task to Firstmate (never straight to the worker). Every run shows its cost at list price, tokens, model and time, and the panel adds up what this PR version has cost; the model and effort can be picked per run.
- **Logbook** (the **Logbook** tab, which opens on **Headroom**): the session and headroom pages, and a **Plugins** tab that opens **Settings → Plugins**. The session and headroom pages each have a quiet piece on the home page's rail (the allowance under its headline, an estimate on each card under way, **Decided for you** with the latest three calls, and **Where time went today**) and a page of its own:
  - **Decided for you** (`/decisions`): review questions the automated review raised that Firstmate answered on your behalf, newest first, grouped by day and filterable (Fix it, Keep as is, No change, Defer). Each opens to show the question, Firstmate's call and its reason (the reviewer's full note is folded away), whether the work has landed, **I'd decide differently** (opens the chat with the task mentioned and a draft to finish) and **Chat about this**. Questions that carry your own words (prototype reviews and other captain calls) are never listed.
  - **Where time went** (`/time`): for today, the last 7 or 30 days, each task's time split into building, automated review and fixes, Firstmate deciding, CI checks and waiting on you, on one shared scale, with per-project totals and how long work usually takes from start to ready for you.
  - **Headroom** (`/headroom`): how much of your Claude allowance is left, when each window resets and whether the recent pace lasts until then; who on this machine is using Claude (Firstmate, each task with its share of automated review, other use) over the last 5 hours or 7 days; and use per hour for the last day. When a window will run out before it resets, a warning shows in the header on every page. **Ask Firstmate to hold new work** drafts that message in the chat. If quota-axi needs its one-time Keychain approval, the page and the rail say **Connect your Claude usage** and give the command (`quota-axi --allow-keychain-prompt`) to run once yourself; Wheelhouse never asks for that approval.
- **Settings** (the gear in the header), with two pages: **Gateway** (`/settings/gateway`, where it opens): the messaging gateway's channels, whether each is connected, the account it is paired with and which alerts it sends (see [The messaging gateway](#the-messaging-gateway)); and **Plugins**, below.
- **Work-time estimate**: work under way shows a rough estimate of the work time left before it is ready for your review ("About 20 min left · rough guide"), on its rail and Harbour cards and, with the steps still ahead, on its task page; "Taking longer than usual" when similar work had finished by now; prototypes and scouting show their time under way with "no set end". It is worked out from finished work of the same kind (this project's when it has at least three, else across projects): what similar work still had left at the same point, as a median with a 25th–75th percentile range, labelled an early guess, a rough guide or a good guide by how much history there is and how much it agreed. The task page also shows where the task's time went and the review questions Firstmate decided on it.
- **Project passage** (`/projects/<id>/passage`, linked from each project's header and its card on Projects): the steps and checks the project's passage declares, where each came from, and any problem with its passage files, plus the switches that enable a project file's network checks and allow the passage's command checks, each listing exactly what it turns on. **Edit passage** opens the passage editor (`/projects/<id>/passage/edit`): see [Editing a passage in Wheelhouse](passages.md#editing-a-passage-in-wheelhouse).

- **Settings → Plugins** (`/settings/plugins`, from the gear in the header or the Logbook's **Plugins** tab; `/plugins` leads there too): every plugin, built in or installed from GitHub, each with a switch that turns it on or off for every project, and in plain words where it is on now (say **On for 3 of 7 projects**), or why it was refused or could not be loaded. Where that differs from project to project (a project's own choice, or a plugin on only where a project has its file), the switch sits half-way. Turning it on or off for every project replaces each project's own choice, so it first asks, naming the choices it replaces, whether to turn it **On for every project** or **Off for every project**; **Back to the default** is beside it once you have used it, and keeps the projects' choices. The switch and everything on a plugin's own page are saved to Wheelhouse's plugins file (`plugins.json`, made when there is none yet) and apply straight away, with no restart; the page says so each time. A plugin's own page (`/settings/plugins/<id>`) has **Where it is on**: where it is on now and the same switch for every project, with **Back to the default** once you have used it, and each project's choice of **As the plugin**, **On** or **Off**; **Settings**: the settings it declares, as the same form the install dialog shows, saved with **Save settings**; and **About**: what it adds, where it comes from, its version and where it is on by default. An installed plugin that is turned off is not loaded at all, so its page offers **Load and restart**, which turns it back on and restarts Wheelhouse to load it (Firstmate and its crew keep running). Each installed plugin says when it has something newer (**Check for updates** checks now; Wheelhouse also checks when the last check is over six hours old) and offers **Update**, or **Move to** a newer release tag for one installed at a tag. **Install plugin** installs one from an `org/repo`. Both show what they would install and ask for its settings before they do, then restart Wheelhouse to load it. While the plugins file is not valid, every plugin keeps its default and nothing on these pages can change it until it is fixed. See [Plugins](plugins.md#from-the-plugins-page).
- **Plugins** add to fixed places on these pages: a project tab (linked beside a project's name and on its scoped Harbour view, each its own full-window page at `/projects/<id>/<plugin>/<tab>`), a card in the project's Harbour section, a section on the task page, evidence under one passage step, a card under a Firstmate reply in the chat that links something the plugin knows, a tab on the home page's rail, a small header indicator and a top-level menu page. In any of them but the header and the chat's cards, a plugin can draw an MCP app: the UI its own MCP server offers for one of its tools, in a sandboxed frame, where a call that may change something waits for your agreement (see [MCP apps](plugins.md#mcp-apps)); when Firstmate itself calls a tool on a plugin's MCP server that has an app, such as docket's search, the app sits under its reply as a closed card you can open (see [MCP apps in the chat](plugins.md#mcp-apps-in-the-chat)). Wheelhouse ships three: **Project links** (bundled in the installed-plugin format, and off until you turn it on in **Settings → Plugins**): a project's repository, README and pull requests, the task's branch, and a compare link under the Pull request step; **GitHub issues** (bundled the same way, and off until you turn it on; its labels, assignee and what happens to a new issue are set on its page there): the open issues you watch in each project's repository (by default labelled `ready-for-pr` or assigned to you), which ones Firstmate already has in hand, a **Hand to Firstmate** link that fills the message box, and per project either a bell ring or an automatic handoff for each new one; and **Vault** (bundled the same way, and on): a **Vault** menu page, a project's **Secrets** tab and a task's **Secrets used** tab, with secrets by name only, never a value. On the Vault page you add a secret (a name, a value typed once and never shown again, and the projects that may use it), open one to tick or untick the projects that may use it, replace its value or remove it; it is there even before the vault holds anything (see [The vault](vault.md#in-wheelhouse)). More can be installed from their own repositories with `wheelhouse plugin install <org/repo>`, such as docket's (`wheelhouse plugin install chrisjowen/docket`), a read-only chart of a project's docket, and improve's (`wheelhouse plugin install chrisjowen/improve`), which adds an **Improvements** menu item listing improve's proposals for Firstmate's harness; while the Firstmate home uses improve and its plugin is not installed, the Plugins page says so, with that command. See [Plugins](plugins.md).

Everything you type goes to Firstmate. There is no way to message a worker directly and no worker controls anywhere. Wheelhouse writes nothing into the Firstmate home, except a project's `.wheelhouse.yaml` in its clone when you save it in the passage editor; it types into the Firstmate session it runs, and sends to a session running elsewhere only through `fm-inbox.sh note`.

### The Firstmate session

`wheelhouse open` starts the one Firstmate session when none is running: an ordinary interactive `claude` in Firstmate's checkout, inside a detached tmux session named `wh-firstmate` on Wheelhouse's own tmux server (`tmux -L wheelhouse`; change the name with `--tmux-socket <name>` or `WHEELHOUSE_TMUX_SOCKET`), never the default server the crew run on. It is the same session you would start in a terminal, so Firstmate's own hooks and supervision run unchanged.

- **One session only.** Firstmate's session lock decides: when `fm-inbox.sh ready` says another session holds it (say, Firstmate running in your own terminal), Wheelhouse starts nothing and shows that session's conversation read-only, since it cannot type into a terminal it does not own; the message box then sends to Firstmate's inbox (`fm-inbox.sh note`, see [Messages and retries](architecture.md#messages-and-retries)), and Firstmate's reply appears in the conversation. If the lock cannot be read, it starts nothing either. If starting fails, **Start Firstmate here** on the home page tries again, under the same rule.
- **It outlives Wheelhouse.** The session belongs to tmux, so closing the browser or Wheelhouse leaves it running, and the next `wheelhouse open` shows it again. To use your own terminal, run `tmux -L wheelhouse attach -t wh-firstmate`.
- **Permissions.** It starts with `--dangerously-skip-permissions` (and Claude Code's bypass-mode confirmation skipped), so Firstmate runs without stopping to ask; `--no-skip-permissions` starts it without, and Claude Code's permission prompts then appear in the terminal drawer. Before starting it, Wheelhouse pre-approves Claude Code's workspace trust for Firstmate's checkout (`hasTrustDialogAccepted` in `${CLAUDE_CONFIG_DIR:-$HOME}/.claude.json`, written atomically; no other setting is touched). `FM_HOME` is passed when the home differs from the checkout.
- **Its transcript.** Wheelhouse adds one SessionStart hook of its own through `claude --settings` (merged with Firstmate's hooks, never replacing them), which writes the hook's input, including `transcript_path`, to `<state-dir>/firstmate/session-start.json`. The chat follows that file, and finds the new one after `/clear`, `/compact` or a restart. For a session it did not start, it looks up the Claude session id Firstmate records beside its lock (`state/.lock-session`), else the newest transcript whose records name Firstmate's checkout. It only ever reads the transcript, and reads at most its last 8 MiB when first opening it (earlier messages stay in the terminal).

The chat shows the captain's messages (including ones typed while Firstmate was busy), Firstmate's replies as Markdown, and its work between replies folded into one line ("3 commands, 1 skill"; "Thought for 7s") that opens to a row per step and then to the step's input and result. Claude Code records only a sealed signature for its thinking, so thinking shows as how long it took, not the words. A turn started by a background wake (a task notification) whose reply is empty or only an all-clear such as "Captain, shipshape." is kept out of the chat; the **ship health** pill in the chat's bar (All well, N need you, Keeping an eye on a problem, Something failed) says when the last background check ran, or that one is running, and lists recent ones. A wake with something to say reads as an ordinary message. Slash commands and their output show as they do in the terminal.

- **Typing.** Enter sends, Shift+Enter adds a line. A message shows in the chat at once, faded, with where it is: **Sending…**, **Queued** (Firstmate was busy, so Claude Code holds it until the turn ends), **Delivered** (waiting for it to appear in the session), or **In Firstmate's inbox**; it becomes an ordinary message when the session's transcript records it, in whatever form Claude Code hands it over (a large paste wrapped in its paste tags, several queued messages delivered as one, or a mid-turn reminder). A mid-turn reminder shows as your message at the point Firstmate read it. One the transcript never shows recognisably is let go once Firstmate has finished two turns since, rather than staying faded below them. If it could not be sent, it says why and offers **Retry** and **Discard**. The message is pasted into the session as one bracketed paste (`tmux load-buffer` and `paste-buffer -p`), then Enter, so a multi-line message never submits early. `/` at the start offers Firstmate's commands (its skills marked `user-invocable: true` and its `.claude/commands`) and the Claude Code built-ins that work from a chat (`/compact`, `/clear`, `/context`); built-ins that open a picker in the terminal are left out. Typed anyway (`/mcp`, `/model`, `/config` and the like), such a menu shows in the chat as a card: numbered choices as buttons, and otherwise **Close menu**, which presses Escape only while the menu is on screen (as often as its nested screens need), and **Use it in the terminal**. While any menu or question is open, nothing is typed into the session, where Enter would choose in the menu: your message waits in the box until it closes. `#` anywhere offers tasks and pull requests and inserts a chip, which Firstmate receives as `[task <id>: <title>]` (or `[PR <url> — task <id>: <title>]`), the task id being the key its own scripts use. While Firstmate works, an empty message box offers **Stop**, which presses Escape in the session.
- **Replying.** To answer a particular message, yours or Firstmate's, as in WhatsApp: hover over it and click the reply arrow beside it (or tab to it), or on a phone swipe the message to the right, or hold it to show the arrow. The start of that message shows above the message box, with a cross (or Esc) to cancel. The sent message carries the quote at its top; click the quote to scroll back to the original, which lights up for a moment. Firstmate only receives text, so the quote reaches it as one Markdown line before your words: `> Replying to Firstmate: “<the first 140 or so characters, as plain text>”`, a blank line, then your message (`Replying to my message` for one of yours). The chat recognises that form when it comes back in the transcript and shows it as a reply. A slash command typed while replying is sent as the command alone, without the quote, so it runs. A quote whose message is no longer in the chat (it shows only the most recent part of a long conversation) still shows, but leads nowhere. A message of attached files alone has no words to quote, so it offers no reply. There is no reply while Firstmate cannot be messaged.
- **Attaching files.** The paperclip at the left of the message box attaches files; so does dropping files anywhere on the chat, or pasting an image or file into the box when the clipboard holds no text (pasted text is typed as before, even when the clipboard also holds a picture of it). A pasted image with no name of its own (a screenshot, say) gets one like `Pasted image 2026-10-31 09.05.07.png`. Each file uploads at once and is listed under your text with its kind and size (an image with a small thumbnail), how far it has got, or why it failed; the cross removes it, stopping an upload still under way. Send waits until uploads finish, and a message can be files alone. A file may be up to 25 MB; a larger one says so and is not uploaded. Firstmate receives your words followed by one line per file, `[attached file <absolute path> — <name>, <size>, <type>]`, and opens the file with its own tools (with `--no-skip-permissions`, reading a file outside its checkout may ask first, in the terminal drawer). In the chat the message shows a **N files attached** card listing each file, with a thumbnail for a PNG, JPEG, GIF, WebP or AVIF image (click to enlarge), and keeps it once the transcript records the message. This works the same when messages go to Firstmate's inbox.

  Files are kept on this machine in Wheelhouse's state directory, `<state-dir>/uploads/<day (UTC)>/<random id>/<name>` (by default `~/.local/state/wheelhouse/uploads/`), never in Firstmate's home, a project clone or a git repository, readable only by your user. Names are cleaned (no folders, control characters or characters shells treat specially; at most 120 characters, extension kept). Wheelhouse deletes each day's folder seven days later, when it starts and whenever a file is attached; a message older than that still lists its files, without thumbnails. Uploads use the same guard as every change (loopback `Host`, the page's own `Origin` and this launch's session token). Wheelhouse never runs an uploaded file or renders it as a page: thumbnails are served only for files whose bytes are one of those image formats, with that type, `X-Content-Type-Options: nosniff` and a sandboxing `Content-Security-Policy`; anything else, SVG and HTML included, is listed by name only.

- **Dictating.** The microphone beside Send (also under a preview) dictates into the box: click it, or press Ctrl/⌘+Shift+Space in the box; held down, the shortcut listens until you let go. Words appear as you speak, the part still being recognised in a lighter colour, and stay as ordinary text to edit; nothing is ever sent for you. Click again to stop, Esc to cancel and put the box back, or just start typing. Dictation uses the browser's Web Speech API, which Chrome and Edge provide by sending the audio to their speech service (Google, in Chrome); Wheelhouse says so once before first use. In a browser without it, or with the microphone blocked, the mic says so plainly. The engine sits behind a small interface (`src/lib/voice/engine.ts`) so a private local engine can be added later.
- **Questions.** When Firstmate asks with Claude Code's question picker, the chat shows the question with its options as buttons; picking sends the keys the picker expects, worked out on the server from the open question. Free-text answers go through the terminal.
- **The terminal drawer** shows the session's own screen, live, for anything the chat cannot show. Its full-screen button puts it in the browser's full screen (filling the window where the browser refuses), keeping the same connection; the terminal refits to the new size and the session's tmux window follows. Esc still goes to the session where the browser allows it (hold Esc to leave full screen; elsewhere Esc leaves it), and the button beside it restores the drawer. It is a WebSocket at `/api/firstmate/terminal`, served on `127.0.0.1` only, backed by a real pty (`node-pty`) running `tmux -L <socket> attach-session -t =wh-firstmate`.

Everything that types into the session (sending, Stop, answering, closing a menu, the terminal) is refused unless its `Host` is loopback, its `Origin` is the page's own and it carries this launch's session token (as a WebSocket subprotocol for the terminal), and it reaches only `wh-firstmate` on Wheelhouse's own tmux server, and only when Wheelhouse runs it.

### The ship's bell

The bell rings for the moments that matter, on whatever page you are on: **PR green** (a pull request passed its checks and waits on your merge), **Question waiting** (Firstmate is holding a decision for you, or is asking you something in its session: its question picker or a permission prompt), **Worker stuck** (a worker reported itself blocked or failed, Wheelhouse lost contact with it, or a working task has had no word for 20 minutes with nothing running), **Merge landed** and **New issue** (a GitHub issue you watch, for projects whose GitHub issues setting is **Ring the ship’s bell** (`bell`); see [Plugins](plugins.md#github-issues)). Each shows as a toast at the top right, under the header and clear of the chat's message box, newest first, with one-tap actions: **Merge** (on a green PR), **Open decision**, **Answer in chat**, **Open task**, **Ask Firstmate**, **Open PR** and, on a new issue, **Hand to Firstmate** (a note with the issue's URL, repository and title, sent once). **Merge** never merges anything itself: it sends Firstmate a note asking it to merge that pull request, through `fm-inbox.sh note` like any other message, and says **Asked Firstmate to merge** once Firstmate has it; a second tap, or a tap in another tab, sends nothing more. Three toasts show at once; the rest fold into **+N more**. News closes itself after a few seconds (not while the pointer is on it); a toast that waits on you stays until you dismiss it or its moment passes (the PR merged, the question answered, here or in the terminal).

Wheelhouse raises each alert once while its moment lasts (a moment that passes and comes back, such as a PR that goes green again after rework, rings again), on the server, from the same records it already reads, and only for moments that happen while it is running: what is already true when it starts is on the board, not news. Your browser remembers what it has rung, so an alert rings once however many Wheelhouse tabs are open and however often you reload; a toast you dismissed stays dismissed in every tab. The tabs share one connection to Wheelhouse (one tab holds it and passes events to the others, and another takes over when that tab closes), so many open tabs never use up the browser's connections.

The bell in the header lists the recent alerts and holds this browser's settings: which kinds ring, **Bell sound** (two strokes of a ship's bell, off until you turn it on; **Ring the bell to hear it** plays it), and **Browser notifications** (off until you turn them on, which asks the browser's permission). A notification shows only when no Wheelhouse tab is in front, and selecting it opens the task, never a merge. The tab you are looking at plays the sound; with none in front, the tab holding the connection does. Toasts come and go without moving when your system asks for reduced motion.

### The messaging gateway

The gateway lets you reach Firstmate from your phone, through a Discord bot of your own. It is part of Wheelhouse itself, not a plugin, and Discord is its only channel for now.

- **Messages to Firstmate.** A direct message you send the bot goes to Firstmate through `fm-inbox.sh note`, exactly like a message sent from the browser, with a first line (`[via Discord] …`) saying it came from your phone and asking Firstmate to answer with `fm-inbox.sh reply`. Its request id is the Discord message's own id (`discord:<id>`), so a message Discord delivers twice is still one note. Reply to one of the bot's alerts or decisions (or to one of Firstmate's answers) and your message is about that task (`Re: <task>`). The bot marks your message 📥 once Firstmate has it and 👀 once Firstmate has read it, and Firstmate's reply comes back under it. Only text is passed on: attachments, stickers and forwards are not, and the bot says so. `status` (the crew at a glance, from what Wheelhouse already reads) and `help` are answered by Wheelhouse itself and wake nobody. At most 6 messages a minute and 200 a day are passed on, since each one wakes Firstmate.
- **Alerts and decisions.** The [ship's bell](#the-ships-bell)'s alerts of the kinds you pick (**Question waiting**, **PR green** and **Worker stuck** to begin with) arrive as messages. **Merge** on a green PR is a button that sends the very note the browser's **Merge** sends, with the same request id, so a tap on the phone and a click in the browser ask Firstmate once. A question with a card in **Decisions** arrives as that card, its **Approve**, **Fix** and **Skip** as buttons. A question whose text names options never sends picks you did not see: a single call's options are buttons of their own (each sends that pick) when they fit beside **Fix**, **Skip** and any **Open PR** link; otherwise, and always with **Titles only** on, the picks are made in Wheelhouse, through an **Open in Wheelhouse** link. Once the card is answered, here or in the browser, or closed, a button sends nothing more and says why. Pull request links open on the phone; Wheelhouse's own pages are on your Mac's loopback, so **Open in Wheelhouse** opens only on that Mac, and alerts leave them out. A button holds only a random token for an action Wheelhouse keeps: it works once, for 24 hours, and only for you.
- **Never from a chat.** Nothing you send the bot types into the Firstmate session, answers its question picker or its permission prompts, or reaches a worker. A question Firstmate asks in its session arrives as a notice to answer it at the keyboard.
- **Who is heard.** Only the account you pair. Anyone else who messages the bot gets no answer at all, and messages in server channels are ignored, yours included. Pairing binds your Discord user id, which never changes, not your name.
- **The bot token** is set only with `wheelhouse gateway connect discord`, which asks for it with the input hidden (or reads it from stdin), never from the command line, where other processes could see it. It is kept in the macOS Keychain (a password item for the service `wheelhouse-gateway`, account `discord:<digest of the gateway directory>`, so each config directory has its own token and a Wheelhouse started with another `--config-dir` starts with none), written through `security`'s standard input so it never appears on a command line either. Where the Keychain cannot be used, it is kept alone in `<config-dir>/gateway/discord.token` (see `--config-dir`) instead, readable by your user only. Either way it is never in the Firstmate home, a project or a worktree, never in the environment of anything Wheelhouse starts, and never in a log. A config directory inside the Firstmate home keeps the gateway off. The gateway's other settings (on or off, the paired account, the alerts, titles only) are in `<config-dir>/gateway/settings.json`.
- **What leaves your Mac.** Alerts (the task's title and one line about what happened), decision questions, Firstmate's replies and the `status` summary go to Discord, which does not encrypt bot chats end to end. No diffs, terminal output or screenshots are sent. With **Titles only** on, alerts and decisions say only what kind of alert it is and which task (a decision, only its task): no alert text, question or recommendation. Their buttons and pull request links stay.
- **Only while Wheelhouse runs.** The gateway runs inside Wheelhouse's server and only connects out to Discord (one WebSocket, and HTTPS calls); it opens no port, so Wheelhouse still listens on `127.0.0.1` only. For use away from the keyboard, leave Wheelhouse running, for example `wheelhouse open --no-browser` in tmux, and keep the Mac awake. Run one Wheelhouse per bot: two would both answer the same messages.
- **Its record.** Which phone messages it passed on and the buttons it handed out are kept in `gateway.json` beside the home's messages in the state directory; every message accepted or refused (with why), every send and every press is logged in `<state-dir>/gateway/discord.jsonl`.

#### Setting up Discord

You need a Discord account, with two-factor authentication on (whoever holds the account can message Firstmate), and a server of your own for the bot to share with you: a bot can only exchange direct messages with people it shares a server with.

1. Open the [Discord Developer Portal](https://discord.com/developers/applications), choose **New Application**, name it (say, Wheelhouse) and create it.
2. On **Installation**, set **Install Link** to **None**: Discord will not make a bot private while it has one.
3. On **Bot**, turn **Public Bot** off, so that only you can add it to a server. Leave **Presence Intent**, **Server Members Intent** and **Message Content Intent** off: Wheelhouse asks only for direct messages, which need none of them. Choose **Reset Token** and copy the token (Discord shows it once).
4. In a terminal on the Mac that runs Wheelhouse, run `wheelhouse gateway connect discord` and paste the token at the prompt. Wheelhouse checks it with Discord, warns if the bot is still public, saves it, and prints a link that adds the bot to a server.
5. If you have no server of your own, create one in Discord (**+**, then **Create My Own**). Open the link from step 4 and add the bot to that server; it needs no permissions. Keep **Direct Messages** on in the server's **Privacy Settings**.
6. In Wheelhouse, open **Settings** (the gear in the header). Within a few seconds Discord shows **Connected** as your bot. Choose **Pair an account**: a code shows for ten minutes.
7. In Discord, open a direct message with the bot (its name in the server's member list, then **Message**) and send the code. The bot answers that you are paired, and Settings shows your account.

Tick which alerts arrive, and whether they come as titles only, in Settings → Gateway. To stop, use **Turn off** there or the commands below. If the token may have leaked, choose **Reset Token** in the Developer Portal (the old token stops working at once) and run `wheelhouse gateway connect discord` with the new one.

| Command                                  | Does                                                                                                                              |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `wheelhouse gateway connect discord`     | Set the bot token (asked for, hidden), after checking it with Discord; it replaces the one before                                 |
| `wheelhouse gateway off` / `on`          | Turn Discord off (it neither reads nor sends) or on again                                                                         |
| `wheelhouse gateway unbind`              | Forget the bound account; no one is heard until you pair again                                                                    |
| `wheelhouse gateway titles-only on\|off` | Send alerts and decisions as titles only, or in full again                                                                        |
| `wheelhouse gateway status`              | Where the token is kept, on or off, who is bound, the alerts, titles only, and the running Wheelhouse's connection (`--port <n>`) |

Each takes `--config-dir <dir>`, and a running Wheelhouse picks up the change within a few seconds.

### The PR review

The review agent is your local `claude` CLI in headless print mode (`claude -p`), run only when you press a button: nothing runs when a page opens. It gets no tools at all (`--tools ""`), no MCP servers, hooks, plugins, skills or CLAUDE.md (`--safe-mode`), no saved session, and a spending cap per run (`--max-budget-usd`, `$WHEELHOUSE_REVIEW_MAX_USD`, default 1), so it can only read what Wheelhouse gives it and answer; it never changes code. Wheelhouse gives it the pull request's committed diff (from the task worktree, else `gh pr diff`; at most about 160 KB, with boilerplate listed by file only) and the task's records: `data/<id>/brief.md`, the commit messages, the PR description, the automated review's findings with Firstmate's call on each, the worker's questions and Firstmate's instructions, and what each check step did.

The guide is kept per pull request version (its head commit), so reopening it costs nothing; once a fix is pushed the old guide is offered as out of date and **Prepare the guide** writes one for the new version. At most two runs go at once, and any can be stopped. Answers stream over the page's existing live connection (`/api/events`), so the review adds no connection of its own. `--review-model` and `--review-effort` (or `WHEELHOUSE_REVIEW_MODEL` and `WHEELHOUSE_REVIEW_EFFORT`) set the defaults, a mid model at low effort; `WHEELHOUSE_REVIEW_CLAUDE` names a different `claude` binary, and `WHEELHOUSE_REVIEW_AGENT=0` turns the agent off (the diff still shows). It signs in with your claude.ai login, the way your own Claude Code does: an `ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN` in Wheelhouse's environment is not passed on unless `WHEELHOUSE_CLAUDE_USE_API_KEY=1` asks for key-based billing. The cost shown is the CLI's own figure at list price; on a Claude subscription it comes out of your allowance rather than being billed per run.

### Passage steps

| Work  | Steps                                                            |
| ----- | ---------------------------------------------------------------- |
| Ship  | Queued → Building → Checks → Pull request → Your review → Landed |
| Scout | Queued → Scout → Report → Your call → Done                       |

The steps follow Firstmate's delivery mode: direct-PR work has no local Checks step, local-only work has no Pull request step, and with yolo on there is no Your review step because Firstmate merges the work itself. In no-mistakes mode the pipeline opens the pull request before CI runs, so CI checks appear under Pull request. Its CI monitor keeps running until the pull request merges, so an open, non-draft pull request whose checks are green moves to Your review (and **Needs your review**) even while that monitor is still working. Whose review it is comes from GitHub, not a guess: when its review is requested of other people, or the base branch requires an approval and you opened the pull request yourself (GitHub never counts the author's own approval), it is **Waiting on reviewers** instead ("Pull request #12 is waiting on approval from @alice"), with the reviewers named, and it does not count as needing you. A review requested of you is yours, and once GitHub says it is approved it is yours to merge ("approved and ready for you to merge"). Once you ask for changes after it was reported ready, it is the worker's turn and the task starts a new **run**. A change sent from Wheelhouse goes, through Firstmate, to the worker that opened the pull request while that worker is still live, so no second session starts; only when that worker is gone does Firstmate start a new one for the run (see [Messages and retries](architecture.md#messages-and-retries)). Runs are counted the same way either way: run 1 is the first build up to its ready report, and run 2 (then 3, and so on) goes back to the start of the build cycle, Building, then Checks once its validation run starts, then Pull request once it pushes or its CI runs, and Your review when the worker reports the pull request ready again. Cards, On deck, the radar (whose dot moves back to Building) and the task page name the run with its step ("Run 2 · Building"), and the merge call leaves the Decisions inbox until the run is ready. Asking for changes is any of: a review comment on a file or line, a changes-requested review or a commented review that says something, or a comment on the pull request on GitHub that is more than approval or merge chatter (a comment that is only "LGTM", "looks good", "approved", "ship it", "merging after lunch" or emoji does not count; one that adds anything, such as "LGTM once the docs are updated" or a question, does); new commits pushed to it; feedback typed under the live preview, a change asked from Wheelhouse's PR review, or **Fix** / **Request changes** in the Decisions inbox; or a `working:` status line from the worker after the ready report. A plain chat message does not start a run, since it may only be a question; use one of those actions to ask for changes. Wheelhouse keeps the change requests it sent (the latest 2000) apart from the other messages in its message record, so a task's runs do not depend on how many other messages have been sent since. The worker's next ready report ends the run and hands the pull request back to you, whether or not it pushed new commits (it may have only answered a question). Feedback from bots never counts, and neither do replies inside a review thread; the pull request author's own comments count only when the author is the account Wheelhouse reads GitHub as (you reviewing a pull request opened under your account), since otherwise the author is the worker. On the task page, **Stages** starts with the runs (each with how it went: how long it took to build, and how many changes were asked of it); the current run shows the changes that started it as a checklist above its stages (each request with where it came from, its file and line and a link to it on GitHub, ticked once its thread is resolved on GitHub or the worker has reported the pull request ready since), and selecting an earlier run shows its changes, its stages, the validation runs and screenshots from that run, and its times. A card counts the current run's changes ("Run 2: 2 changes to make · 1 done"). These built-in passages are written in the passage file format (`src/lib/server/passages/builtin.ts`), and a project can add steps such as Deployed or Released to them with a [passage file](passages.md).

### Honest gaps

Wheelhouse shows what Firstmate records and says plainly what it cannot see:

- **Deployments** are not recorded by Firstmate. A Deployed (or Released) step, and the watch report's "N live", appear only for projects whose [passage file](passages.md) declares one and the checks that observe it.
- **Preview links** appear only when a worker reports one with a `preview <url>` status line.
- **Decisions** Firstmate holds for you are recorded as text, without structured options. The **Decisions** inbox reads the options from that text where it can: lettered options (A, B, C), numbered calls each with their own options ("1) Approach: A … or C …", "(1) … yes / no", "Q1: …"), the one marked (recommended) or (rec), which starts picked, and a closing question, which becomes an optional yes/no. Each call shows as a set of choices, a call that cannot be split cleanly takes a written answer, and a report the question names (a Markdown file in Firstmate's `data/` folder) opens in the card with **Read the report**. **Send picks** sends Firstmate your picks as one line ("1) Approach: A (core gateway) 2) First channel: Telegram 3) WhatsApp: Skip for now") with your note. Text with no options it can read keeps the Approve / Fix / Skip choices and the note. Either way the answer goes to Firstmate as a message; you can also answer in the chat. **Close** (or `c`) takes a question that no longer needs you off the stack without an answer: a review question, a worker's decision, a stuck worker or a preview sign-off, answered or not, as long as Firstmate records it under a decision key. Wheelhouse asks Firstmate to record it resolved on its decision key, and the card leaves at once (it comes back only if the question is raised again). A captain hold or a merge call closes by being answered. Questions Firstmate asks with Claude Code's question picker show as buttons.
- **The messaging gateway** works only while Wheelhouse runs, and only through Discord for now.
- **Firstmate's thinking** is not shown as words: Claude Code keeps only a sealed signature for it.
- **Inbox messages** (sent when Firstmate runs in another terminal) report delivery and acknowledgement as a yes/no: Firstmate does not record when it acknowledged a message.
- **Current state** comes from Firstmate's current-state read. Status-log lines are shown as history, never as the current state, and terminal output is a bounded sample, not a transcript.
- **Stale data** is labelled: if Wheelhouse cannot read Firstmate, it keeps the last view and says how old it is.
