# Using Wheelhouse

Everything Wheelhouse does, page by page, and how it runs Firstmate. For the short version, see the [README](../README.md).

## Requirements

- Node.js 22 or newer, and npm.
- A Firstmate checkout and its operational home (the directory with `state/` and `data/`). Wheelhouse starts Firstmate's session there when none is running (see [The Firstmate session](#the-firstmate-session)); it never stops or reconfigures Firstmate.
- Whatever Firstmate's own scripts need (bash, python3, git).
- Optional: the GitHub CLI (`gh`), used to read a pull request's state and checks when Firstmate has no cached observation of it, and by the GitHub checks a [passage file](passages.md) declares.
- `tmux` and Claude Code (`claude`) on your `PATH`, to run and talk to Firstmate from Wheelhouse. Without them Wheelhouse says so, still shows a Firstmate session running elsewhere (read-only), and the rest works as usual.

## Use

Run it inside a Firstmate checkout:

```bash
wheelhouse open
```

Or give the paths:

```bash
wheelhouse open --firstmate ~/firstmate --home ~/crew --port 4310
```

| Option                  | Default                                                                                           |
| ----------------------- | ------------------------------------------------------------------------------------------------- |
| `--firstmate <dir>`     | the Firstmate checkout you are in                                                                 |
| `--home <dir>`          | `$FM_HOME`, else the Firstmate directory                                                          |
| `--port <n>`            | `4310`                                                                                            |
| `--state-dir <dir>`     | see below                                                                                         |
| `--config-dir <dir>`    | see [Passage files](passages.md)                                                                  |
| `--tmux-socket <name>`  | `$WHEELHOUSE_TMUX_SOCKET`, else `wheelhouse`; see [The Firstmate session](#the-firstmate-session) |
| `--no-skip-permissions` | start it with `--dangerously-skip-permissions`                                                    |
| `--spec-model <model>`  | `$WHEELHOUSE_SPEC_MODEL`, else `sonnet`: the model the Spec tab's interviewer uses                |
| `--spec-effort <level>` | `$WHEELHOUSE_SPEC_EFFORT`, else `low` (`low`, `medium` or `high`)                                 |
| `--no-browser`          | open the browser                                                                                  |
| `--review-model <m>`    | `$WHEELHOUSE_REVIEW_MODEL`, else `sonnet`; see [the PR review](#the-pr-review)                    |
| `--review-effort <e>`   | `$WHEELHOUSE_REVIEW_EFFORT`, else `low` (`low`, `medium`, `high`, `xhigh` or `max`)               |

`wheelhouse` with no subcommand does the same as `wheelhouse open`.

`--state-dir` is where Wheelhouse keeps its own records: the inbox messages it sent (request ids, bodies, delivery outcomes, receipts and the receipts cursor), one file per Firstmate home, `firstmate/session-start.json`, which its SessionStart hook writes to name the Firstmate session's transcript, your spec drafts under `specs/` (one JSON file per spec, with its interview and comments, and its screenshots in a folder beside it), and what the PR review agent wrote, per task and PR version, beside the home's messages (`pr-review/<task>.json`). It defaults to `$WHEELHOUSE_STATE_DIR`, else `$XDG_STATE_HOME/wheelhouse`, else `~/.local/state/wheelhouse`, and must be outside the Firstmate home.

Wheelhouse checks that Firstmate's integration scripts declare the contracts it understands, starts its server on `127.0.0.1` only, and opens the browser. It answers only requests addressed to `127.0.0.1`, `localhost` or `[::1]`; any other `Host` gets a 421, which blocks DNS-rebinding pages. Every request that changes anything (sending a message, starting the Firstmate session, typing into it, stopping it, answering its questions) must also carry an `Origin` equal to the page's own `http://<host>` origin and this launch's session token, which Wheelhouse issues only to the pages it serves; anything else gets a 403. If the scripts look incompatible it still starts, says so in the UI and in `/api/health`, and shows what it can. Press Ctrl+C to close Wheelhouse; Firstmate and its crew keep running.

If Wheelhouse's server dies (a crash, or a process killed outright), a small watcher in `wheelhouse open` restarts it on the same port, up to five times within a minute; if it dies again within that minute, Wheelhouse gives up and closes. The watcher is about Wheelhouse only: it never starts, stops or restarts Firstmate or its crew, and a restarted server does not start a Firstmate session (start one from the home page if you need it). Open pages say plainly when they have lost the server, keep trying, and pick up again on their own once it answers, reloading their data when the server was restarted.

## What you see

The header carries the main sections (Firstmate, Harbour, Projects, Decisions, Spec, Logbook; Decisions with a count of open questions), whether Firstmate is on watch, the project switcher, the [ship's bell](#the-ships-bell) and the light/dark switch. There is no side menu: the pages fill the width under the header, and each section keeps its own pages in a row of tabs at its top (Harbour's **Under way** and **Completed**, with the **Harbour**, **Passage** and **Radar** views beside them; the Logbook's pages). The switcher lists your projects, each with how many things need you: All projects, the ones you pinned, then the most active (waiting on you, under way, latest activity), six in all, then the rest, with a search box that has the keyboard (arrow keys move, Enter picks, Esc closes); choosing a project scopes the page. Projects whose names share a leading part (split on `-`, `_` or `/`) with another project sit under it as a heading, each shown by its own part: `ai-innovations-chat-agent` and `ai-innovations-workflow` read as **chat-agent** and **workflow** under **ai-innovations**, with the full name on hover; one shown on its own reads "ai-innovations › chat-agent", the prefix giving way first. Each project has a two-letter tile from that part (CA, WO) in one of a few quiet colours, so siblings look different. Each row pins or unpins it and renames it: a friendly name, kept in this browser, replaces the shown name everywhere the project is listed and is found by search along with the full name (clear it to go back to the full name).

- **Home** (`/`, the **Firstmate** tab): the conversation with Firstmate, full width, with a rail beside it, **On deck**, on the left by default; the button with two arrows in the chat's bar moves it to the other side, and this browser remembers which. See [The Firstmate session](#the-firstmate-session) for the chat. Under its headline and Claude headroom, the rail shows one list at a time, in tabs that each carry a count (the tab you pick is remembered in this browser): **Under way** (the default), then **Up next**, folded; **Needs you**: a failed step (say, failed checks or a failed deploy) as an urgent card, then pull requests waiting for your review (with their full URLs) and decisions Firstmate is holding for you, in plain words, then **Decided for you**; **Landed** in the last day, then **Where time went today**; and a tab for each plugin card, such as **Harness**. Every card shows its project as a tag (its short or friendly name, as in the project list), what it is doing now (in the checks stage, the same step strip and plain line as on Harbour), a small passage with the current step marked, and a badge for anything wrong, each with an icon and words (Checks failed, Stuck, Not responding, Your review, Your call, Run 2 · Building and the like, Firstmate deciding), and has **Open** (the task page) and **Chat about this** (mentions the task in the message box). A pull request you asked to change after it was reported ready starts a new run (the change goes to the worker that opened it while that worker is still live, and Firstmate starts a new session only once it is gone) and shows under Under way (say **Run 2 · Building**) rather than under Waiting on you, until the worker reports it ready again (see [Passage steps](#passage-steps)). The rail can be resized by dragging its edge (its width is remembered in this browser; a double click restores the default); on narrow screens the chat stands alone and a button opens the rail as a sheet. The project switcher scopes the rail.
- **Harbour** (`/harbour`): the full board. A one-line watch report, then **Your move** (captain-held decisions and pull requests waiting for your review, each showing its screenshot count, the reported live preview link and the pull request link), **Waiting on Firstmate** (decisions a worker raised that Firstmate is handling), and each project's work as cards. A card names the work (its title without the project prefix), who is doing it (harness, model and worker name) and what they are doing **Now**, in plain words with its age: the latest status line, else the latest line of the worker's console. While the work is in its checks stage (a no-mistakes validation run: rebase, review, tests, docs, lint, push, pull request, CI), a slim strip with one segment per step takes the Now line's place, with one plain line under it, for example "Reviewing the change · 1m 20s · 1 question for Firstmate", "Answer received · fixing review findings, round 2 · 3m" or "All checks passed · CI green". The step under way is drawn solid, a step waiting on Firstmate amber and a failed step red; the line says the same in words. Work under way is led by the worker's live console (a bounded, read-only sample of the last lines, refreshed every 2 seconds, only while the card is on screen; select it to open it in the browser's full screen, where the worker's screen is drawn large enough to fill it, refreshes every second and stays where you scrolled to, and Esc or the close button returns to the page); finished work by its latest screenshot or a picture of the diff. A card with screenshots shows the newest few as small thumbnails of one size that open in the in-page viewer. A card whose worker reported a preview has **Show live preview**, which embeds it in the card with **Open in new tab** and a feedback box (see the task page). A soft pulse on the current step shows a worker that is busy right now, and the card counts the files changed, the questions raised about the work (answered and still open) and the docs and decision records the worker's session referenced, read or changed ("5 docs referenced · 2 changed"; it opens the task's Docs tab). While the automated review has questions for Firstmate, the checks line ("3 questions for Firstmate") and the question count open them in the card: each question in a sentence or two (the whole question opens in place), where in the change it is, whether it is still waiting on Firstmate, and once Firstmate answers, its call on that question (fix it, no change, keep as is) and why. It updates as Firstmate answers; the task's **Conversation** tab shows the same questions in each exchange. A project switcher (`?project=`) scopes the page, and the **Passage** view (`?view=passage`) puts every task on one chart. The **Radar** view (`?view=radar`) is the fleet as it moves: one dot per task in five lanes (Queued, Building, Testing, Pull request, Landed), placed by the task's current passage step (a step a passage file adds sits in the lane of the built-in step before it). A dot pulses while its worker is busy, turns amber when it is waiting on you and red (a diamond) when it is stuck: blocked, failed, out of contact or at a failed step; a hollow dot is idle, a brass ring is with Firstmate. Dots glide to their new lane as the live fleet read changes (over the page's one existing event stream), and the line above the lanes counts them by state. Landed dots stay for a day, fading after the first hour. Hover, focus or tap a dot for its card: the project, the task, its current step, how long it has been in its lane and, once the page has seen it change step, in that step, and what it is doing, with a link to the task. Time in the lane counts from when the page saw the task move there, else from Firstmate's records (when its validation run started, when it landed); a status line or the date the task was filed is not a move, and where nothing says, it shows as unknown. Under reduced motion nothing glides or pulses. An **Under way | Completed** toggle switches the cards between work still in progress (including what needs you) and landed or finished work, newest first (`?view=completed`); **Your move** shows only under Under way. A **Large | Compact | List** toggle sets the layout, remembered in this browser: **Large** is the full cards above; **Compact** keeps only the title, a project tag, the status, the passage strip and the question count; **List** puts one row per task with its project, current step, status, who it is waiting on (you, Firstmate, the crew or earlier tasks) and when it last moved, and every column sorts. Each layout keeps the same sections, filters and project grouping.
- **Projects** (`/projects`): every project in Firstmate's project registry, with or without work, as one card each: its description; how many tasks are under way, waiting on you and landed this week; a dot for each open task (it opens the task); its delivery posture in plain words (for example "Product changes run the full checks; internal tooling goes straight to a pull request. Firstmate merges once checks are green."); when anything last happened; and links to its Harbour, its passage and passage editor, any plugin tabs and its repository (from the clone's `origin` remote, GitHub-style remotes only). A **Cards | List** toggle, remembered in this browser, shows the same as one sortable row per project. Picking a project in the switcher opens its Harbour.
- **Task page** (`/tasks/<id>`): full width, in two columns. On the left, pinned while you look around and resizable by dragging its edge as On deck is, the overview: the task's project and crew, its title and state in plain words, what it is doing now, anything waiting on you or Firstmate (while the work waits on your review, its screenshots, live preview link and pull request link come first here), a small passage, a rough time left, **Live preview** and **Ask Firstmate about this** (opens the home page with the task mentioned in the message box), and its pull request, preview, last check and delivery. Under the overview, for work under way, the worker's **Live terminal** (its live console, which folds away), then the task's time: the work-time estimate (the rough time left jumps to it), where the task's time went and the review questions Firstmate decided on it. On the right, tabs (`?tab=`, kept in the link): **Stages** (the default), **Live preview** (while a worker has reported one), **Conversation**, **Checks**, **Docs**, **Screenshots**, a tab for each plugin section, and **Log**; on narrow screens the overview comes first and the tabs follow. **Stages** is the passage as a vertical list: finished stages fold to one line saying what they came to (say "4 files changed" or "Pull request #13 merged"), the current one is open, later ones are faint, and selecting any stage opens or folds it (**Open all** and **Fold all** do every one). An open stage shows the evidence it produced: files changed, the validation run (under Checks: what is happening now, then a short timeline of what each validation step found or changed and how long it took, with the pull request's CI result on the CI step once the PR is up), the pull request and its CI checks, the report and screenshots. Screenshots show as small thumbnails of one size and open in an in-page viewer (Esc closes, the arrow keys step through them), and selecting a changed file shows its diff against the merge base. Status lines show in plain words, with the raw line behind a small **details** disclosure. **Live preview** embeds a reported preview: only a preview on this machine (`127.0.0.1` or `localhost`) is embedded, in a sandboxed frame, after Wheelhouse has checked that it answers; one that does not answer shows **Preview not running**, and one that refuses to be framed says so, with **Open in new tab** either way. The box under it sends your feedback to the task's worker through Firstmate's inbox, as a note about the task (`Re: <task-id>`) that Firstmate passes on (landed work has no worker, so it has no box). **Full screen** (`&full=1`; Esc closes) puts the page on the left and the feedback on the right: everything sent from this preview, with whether Firstmate has it and any reply, and the box to send more. The feedback sits beside the page, so it never covers what you are commenting on, and **Hide comments** gives the page the full width. **Conversation** is the back-and-forth between the worker and Firstmate, oldest first: each question the worker raised (and each time it was stuck), the automated review's questions (each in plain words with where it is in the change, waiting on Firstmate until it answers, then Firstmate's call on it and why), Firstmate's instructions to the worker, and what you sent Firstmate about the task, each saying who asked, who answered and how it ended (answered, still open, read or not yet read by the worker). **Checks** is what each step of the latest validation run found, in plain words, with what each step did: for tests, how many passed and failed, each failed test with the start of its output (select one to see it), and the scenarios the test step drove; for docs, which documentation changed and what the docs step wrote about it. **Docs** lists the decision records and docs the work changed or the worker's session read; each opens as a document in Wheelhouse (`/tasks/<id>/doc?path=`): one readable column on a paper sheet, with its file name, whether the task changed or only read it, a contents list beside it when it has three or more sections, and **Open on GitHub** when the project is there. **Log** has the ship's log (history from Firstmate's fleet ledger) and the raw terminal output, which is read-only and sampled only while it is open and the Log tab is showing; **Full screen** opens it filling the screen, as on a card.
- **PR review** (`/tasks/<id>/review`, from **Review the pull request** on the task page, **Review PR** on every Harbour card with a pull request, and **Guided review** where a PR waits for your review): the task's pull request as a diff, with a guide on top. **Prepare the guide** asks the review agent (see [The PR review](#the-pr-review)) to read the change with the task's records and put the important hunks first (behaviour changes, risky areas, public APIs) under **Read these first**, numbered in reading order. Each says what it does and **why it was done this way**, from the records, with the records it rests on named (the brief's intent and spec, a commit, a review finding and Firstmate's call on it, the PR description, the worker's questions); when nothing records a reason it says **No recorded reason.**, and the agent's own reading is marked **Why: not recorded**. Routine hunks follow, folded; lockfiles, generated files, snapshots, binaries and formatting-only hunks are folded away under **Boilerplate**. Beside it, and staying beside the diff as you scroll on wide screens, **Ask about this pull request**, and under every hunk **Ask, review or request a change here**: ask the agent a question, or **Request review** for a focused review, and the answer streams in where you asked. **Ask Firstmate for a change** sends a note about the task to Firstmate (never straight to the worker). Every run shows its cost at list price, tokens, model and time, and the panel adds up what this PR version has cost; the model and effort can be picked per run.
- **Spec** (`/spec`): a spec built in an interview before you hand work to Firstmate. Say what you want built and the interviewer asks one question at a time: it challenges vague answers, offers two to four answers to pick from (one marked **Recommended**; picking one puts it in the box to send or add to), and says when the spec looks ready (**Ready to build**). Its message streams in as it is written. Beside the interview, the spec fills in after every answer as a document: the title and summary, Problem and goal, Who it is for, User journeys, Scope and non-goals, Requirements (a checklist), UI notes and references, Constraints and risks, and Open questions, with **Not covered yet** under the sections still empty and a brass rule and **Updated** beside the ones the last turn changed. To comment, select words in the spec and click **Comment**, or use a section's comment button; the interviewer addresses open comments straight away (or after the turn it is on), revising the spec or asking a follow-up, and marks each one resolved with what it did. Answers and comments can be dictated. On a narrow screen, **Interview** and **Spec** switch between the two. The interviewer is the local `claude` CLI run headless (`claude -p`, streaming), with no tools that change anything: when the spec's project matches a project with a checkout, it may read that checkout (Read, Grep and Glob) to look facts up instead of asking; otherwise it has no tools at all. It runs without your Claude Code settings, hooks or MCP servers, and without saving a Claude session; each turn it is given the spec, the interview so far and the open comments. Its instructions are your `grilling` skill (or `grill-me`, followed to the skill it runs) from `~/.claude/skills` or `~/.agents/skills` when installed, else a bundled equivalent. It uses `sonnet` at `low` effort unless `--spec-model` and `--spec-effort` say otherwise, and under the answer box it says so, with the turns, tokens and API-price cost of the interview so far (a Claude plan may not bill it that way). `WHEELHOUSE_CLAUDE_BIN` points it at a different `claude`. It signs in with your claude.ai login, the way your own Claude Code does: an `ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN` in Wheelhouse's environment is not passed on unless `WHEELHOUSE_CLAUDE_USE_API_KEY=1` asks for key-based billing (this applies to the review agent too). If a turn fails (no `claude` on the PATH, not signed in), the reason shows with **Try again**; your answer is kept. **Quick form** writes the same spec by hand instead, one section at a time with a prompt and an example each, beside a preview of the document or **As sent**, and takes screenshots for the UI section; the two can be mixed. Specs save as you go, in Wheelhouse's state directory, and **Your specs** lists them, so you can keep several and come back to any, interview and all. Once the spec has a title or a summary and you have chosen its project, **Send to build** opens the chat and sends it there as one message that opens by marking it a build request for that project; screenshots go as file paths Firstmate can open, and a spec too long for one message (over 16 KiB) is written beside the draft as `spec.md` and the message carries its summary and that file's path. It is sent the way the message box sends (typed into the session, or to Firstmate's inbox when it runs elsewhere); if it cannot be sent, the text is left in the message box with the reason. A sent spec is marked **Sent** (or **Edited since sent**) and can be sent again.
- **Logbook** (the **Logbook** tab, which opens on **Headroom**): the session and headroom pages, and the **Plugins** list. The session and headroom pages each have a quiet piece on the home page's rail (the allowance under its headline, an estimate on each card under way, **Decided for you** with the latest three calls, and **Where time went today**) and a page of its own:
  - **Decided for you** (`/decisions`): review questions the automated review raised that Firstmate answered on your behalf, newest first, grouped by day and filterable (Fix it, Keep as is, No change, Defer). Each opens to show the question, Firstmate's call and its reason (the reviewer's full note is folded away), whether the work has landed, **I'd decide differently** (opens the chat with the task mentioned and a draft to finish) and **Chat about this**. Questions that carry your own words (prototype reviews and other captain calls) are never listed.
  - **Where time went** (`/time`): for today, the last 7 or 30 days, each task's time split into building, automated review and fixes, Firstmate deciding, CI checks and waiting on you, on one shared scale, with per-project totals and how long work usually takes from start to ready for you.
  - **Headroom** (`/headroom`): how much of your Claude allowance is left, when each window resets and whether the recent pace lasts until then; who on this machine is using Claude (Firstmate, each task with its share of automated review, other use) over the last 5 hours or 7 days; and use per hour for the last day. When a window will run out before it resets, a warning shows in the header on every page. **Ask Firstmate to hold new work** drafts that message in the chat. If quota-axi needs its one-time Keychain approval, the page and the rail say **Connect your Claude usage** and give the command (`quota-axi --allow-keychain-prompt`) to run once yourself; Wheelhouse never asks for that approval.
  - **Plugins** (`/plugins`): every plugin, built in or installed with `wheelhouse plugin install` (with its repository and pinned commit), and whether it loaded, was refused, failed to load or is turned off, with the reason. See [Plugins](plugins.md).
- **Work-time estimate**: work under way shows a rough estimate of the work time left before it is ready for your review ("About 20 min left · rough guide"), on its rail and Harbour cards and, with the steps still ahead, on its task page; "Taking longer than usual" when similar work had finished by now; prototypes and scouting show their time under way with "no set end". It is worked out from finished work of the same kind (this project's when it has at least three, else across projects): what similar work still had left at the same point, as a median with a 25th–75th percentile range, labelled an early guess, a rough guide or a good guide by how much history there is and how much it agreed. The task page also shows where the task's time went and the review questions Firstmate decided on it.
- **Project passage** (`/projects/<id>/passage`, linked from each project's header and its card on Projects): the steps and checks the project's passage declares, where each came from, and any problem with its passage files, plus the switches that enable a project file's network checks and allow the passage's command checks, each listing exactly what it turns on. **Edit passage** opens the passage editor (`/projects/<id>/passage/edit`): see [Editing a passage in Wheelhouse](passages.md#editing-a-passage-in-wheelhouse).

- **Plugins** add to fixed places on these pages: a project tab (linked beside a project's name and on its scoped Harbour view, each its own full-window page at `/projects/<id>/<plugin>/<tab>`), a card in the project's Harbour section, a section on the task page, evidence under one passage step, a card under a Firstmate reply in the chat that links something the plugin knows, a tab on the home page's rail, a small header indicator and a top-level menu page. Wheelhouse ships three: **Project links** (bundled in the installed-plugin format, and off unless turned on in `plugins.json`): a project's repository, README and pull requests, the task's branch, and a compare link under the Pull request step; **GitHub issues** (bundled the same way, and off unless turned on): the open issues you watch in each project's repository (by default labelled `ready-for-pr` or assigned to you), which ones Firstmate already has in hand, a **Hand to Firstmate** link that fills the message box, and per project either a bell ring or an automatic handoff for each new one; and **Docket** (on for projects with a `.docket.yaml`): a read-only chart of the project's docket. More can be installed from their own repositories with `wheelhouse plugin install <org/repo>`, such as improve's (`wheelhouse plugin install chrisjowen/improve`), which adds an **Improvements** menu item listing improve's proposals for Firstmate's harness; while the Firstmate home uses improve and its plugin is not installed, the Plugins page says so, with that command. See [Plugins](plugins.md).

Everything you type goes to Firstmate. There is no way to message a worker directly and no worker controls anywhere. Wheelhouse writes nothing into the Firstmate home, except a project's `.wheelhouse.yaml` in its clone when you save it in the passage editor; it types into the Firstmate session it runs, and sends to a session running elsewhere only through `fm-inbox.sh note`.

### The Firstmate session

`wheelhouse open` starts the one Firstmate session when none is running: an ordinary interactive `claude` in Firstmate's checkout, inside a detached tmux session named `wh-firstmate` on Wheelhouse's own tmux server (`tmux -L wheelhouse`; change the name with `--tmux-socket <name>` or `WHEELHOUSE_TMUX_SOCKET`), never the default server the crew run on. It is the same session you would start in a terminal, so Firstmate's own hooks and supervision run unchanged.

- **One session only.** Firstmate's session lock decides: when `fm-inbox.sh ready` says another session holds it (say, Firstmate running in your own terminal), Wheelhouse starts nothing and shows that session's conversation read-only, since it cannot type into a terminal it does not own; the message box then sends to Firstmate's inbox (`fm-inbox.sh note`, see [Messages and retries](architecture.md#messages-and-retries)), and Firstmate's reply appears in the conversation. If the lock cannot be read, it starts nothing either. If starting fails, **Start Firstmate here** on the home page tries again, under the same rule.
- **It outlives Wheelhouse.** The session belongs to tmux, so closing the browser or Wheelhouse leaves it running, and the next `wheelhouse open` shows it again. To use your own terminal, run `tmux -L wheelhouse attach -t wh-firstmate`.
- **Permissions.** It starts with `--dangerously-skip-permissions` (and Claude Code's bypass-mode confirmation skipped), so Firstmate runs without stopping to ask; `--no-skip-permissions` starts it without, and Claude Code's permission prompts then appear in the terminal drawer. Before starting it, Wheelhouse pre-approves Claude Code's workspace trust for Firstmate's checkout (`hasTrustDialogAccepted` in `${CLAUDE_CONFIG_DIR:-$HOME}/.claude.json`, written atomically; no other setting is touched). `FM_HOME` is passed when the home differs from the checkout.
- **Its transcript.** Wheelhouse adds one SessionStart hook of its own through `claude --settings` (merged with Firstmate's hooks, never replacing them), which writes the hook's input, including `transcript_path`, to `<state-dir>/firstmate/session-start.json`. The chat follows that file, and finds the new one after `/clear`, `/compact` or a restart. For a session it did not start, it looks up the Claude session id Firstmate records beside its lock (`state/.lock-session`), else the newest transcript whose records name Firstmate's checkout. It only ever reads the transcript, and reads at most its last 8 MiB when first opening it (earlier messages stay in the terminal).

The chat shows the captain's messages (including ones typed while Firstmate was busy), Firstmate's replies as Markdown, and its work between replies folded into one line ("3 commands, 1 skill"; "Thought for 7s") that opens to a row per step and then to the step's input and result. Claude Code records only a sealed signature for its thinking, so thinking shows as how long it took, not the words. A turn started by a background wake (a task notification) whose reply is empty or only an all-clear such as "Captain, shipshape." is kept out of the chat; the **ship health** pill in the chat's bar (All well, N need you, Keeping an eye on a problem, Something failed) says when the last background check ran, or that one is running, and lists recent ones. A wake with something to say reads as an ordinary message. Slash commands and their output show as they do in the terminal.

- **Typing.** Enter sends, Shift+Enter adds a line. A message shows in the chat at once, faded, with where it is: **Sending…**, **Queued** (Firstmate was busy, so Claude Code holds it until the turn ends), **Delivered** (waiting for it to appear in the session), or **In Firstmate's inbox**; it becomes an ordinary message when the session's transcript records it, in whatever form Claude Code hands it over (a large paste wrapped in its paste tags, several queued messages delivered as one, or a mid-turn reminder). A mid-turn reminder shows as your message at the point Firstmate read it. One the transcript never shows recognisably is let go once Firstmate has finished two turns since, rather than staying faded below them. If it could not be sent, it says why and offers **Retry** and **Discard**. The message is pasted into the session as one bracketed paste (`tmux load-buffer` and `paste-buffer -p`), then Enter, so a multi-line message never submits early. `/` at the start offers Firstmate's commands (its skills marked `user-invocable: true` and its `.claude/commands`) and the Claude Code built-ins that work from a chat (`/compact`, `/clear`, `/context`); built-ins that open a picker in the terminal are left out. `#` anywhere offers tasks and pull requests and inserts a chip, which Firstmate receives as `[task <id>: <title>]` (or `[PR <url> — task <id>: <title>]`), the task id being the key its own scripts use. While Firstmate works, an empty message box offers **Stop**, which presses Escape in the session.
- **Dictating.** The microphone beside Send (also in the Spec tab's text boxes and under a preview) dictates into the box: click it, or press Ctrl/⌘+Shift+Space in the box; held down, the shortcut listens until you let go. Words appear as you speak, the part still being recognised in a lighter colour, and stay as ordinary text to edit; nothing is ever sent for you. Click again to stop, Esc to cancel and put the box back, or just start typing. Dictation uses the browser's Web Speech API, which Chrome and Edge provide by sending the audio to their speech service (Google, in Chrome); Wheelhouse says so once before first use. In a browser without it, or with the microphone blocked, the mic says so plainly. The engine sits behind a small interface (`src/lib/voice/engine.ts`) so a private local engine can be added later.
- **Questions.** When Firstmate asks with Claude Code's question picker, the chat shows the question with its options as buttons; picking sends the keys the picker expects, worked out on the server from the open question. Free-text answers go through the terminal.
- **The terminal drawer** shows the session's own screen, live, for anything the chat cannot show. Its full-screen button puts it in the browser's full screen (filling the window where the browser refuses), keeping the same connection; the terminal refits to the new size and the session's tmux window follows. Esc still goes to the session where the browser allows it (hold Esc to leave full screen; elsewhere Esc leaves it), and the button beside it restores the drawer. It is a WebSocket at `/api/firstmate/terminal`, served on `127.0.0.1` only, backed by a real pty (`node-pty`) running `tmux -L <socket> attach-session -t =wh-firstmate`.

Everything that types into the session (sending, Stop, answering, the terminal) is refused unless its `Host` is loopback, its `Origin` is the page's own and it carries this launch's session token (as a WebSocket subprotocol for the terminal), and it reaches only `wh-firstmate` on Wheelhouse's own tmux server, and only when Wheelhouse runs it.

### The ship's bell

The bell rings for the moments that matter, on whatever page you are on: **PR green** (a pull request passed its checks and waits on your merge), **Question waiting** (Firstmate is holding a decision for you, or is asking you something in its session: its question picker or a permission prompt), **Worker stuck** (a worker reported itself blocked or failed, Wheelhouse lost contact with it, or a working task has had no word for 20 minutes with nothing running), **Merge landed** and **New issue** (a GitHub issue you watch, for projects whose GitHub issues setting is `bell`; see [Plugins](plugins.md#github-issues)). Each shows as a toast at the top right, under the header and clear of the chat's message box, newest first, with one-tap actions: **Merge** (on a green PR), **Open decision**, **Answer in chat**, **Open task**, **Ask Firstmate**, **Open PR** and, on a new issue, **Hand to Firstmate** (a note with the issue's URL, repository and title, sent once). **Merge** never merges anything itself: it sends Firstmate a note asking it to merge that pull request, through `fm-inbox.sh note` like any other message, and says **Asked Firstmate to merge** once Firstmate has it; a second tap, or a tap in another tab, sends nothing more. Three toasts show at once; the rest fold into **+N more**. News closes itself after a few seconds (not while the pointer is on it); a toast that waits on you stays until you dismiss it or its moment passes (the PR merged, the question answered, here or in the terminal).

Wheelhouse raises each alert once while its moment lasts (a moment that passes and comes back, such as a PR that goes green again after rework, rings again), on the server, from the same records it already reads, and only for moments that happen while it is running: what is already true when it starts is on the board, not news. Your browser remembers what it has rung, so an alert rings once however many Wheelhouse tabs are open and however often you reload; a toast you dismissed stays dismissed in every tab. The tabs share one connection to Wheelhouse (one tab holds it and passes events to the others, and another takes over when that tab closes), so many open tabs never use up the browser's connections.

The bell in the header lists the recent alerts and holds this browser's settings: which kinds ring, **Bell sound** (two strokes of a ship's bell, off until you turn it on; **Ring the bell to hear it** plays it), and **Browser notifications** (off until you turn them on, which asks the browser's permission). A notification shows only when no Wheelhouse tab is in front, and selecting it opens the task, never a merge. The tab you are looking at plays the sound; with none in front, the tab holding the connection does. Toasts come and go without moving when your system asks for reduced motion.

### The PR review

The review agent is your local `claude` CLI in headless print mode (`claude -p`), run only when you press a button: nothing runs when a page opens. It gets no tools at all (`--tools ""`), no MCP servers, hooks, plugins, skills or CLAUDE.md (`--safe-mode`), no saved session, and a spending cap per run (`--max-budget-usd`, `$WHEELHOUSE_REVIEW_MAX_USD`, default 1), so it can only read what Wheelhouse gives it and answer; it never changes code. Wheelhouse gives it the pull request's committed diff (from the task worktree, else `gh pr diff`; at most about 160 KB, with boilerplate listed by file only) and the task's records: `data/<id>/brief.md`, the commit messages, the PR description, the automated review's findings with Firstmate's call on each, the worker's questions and Firstmate's instructions, and what each check step did.

The guide is kept per pull request version (its head commit), so reopening it costs nothing; once a fix is pushed the old guide is offered as out of date and **Prepare the guide** writes one for the new version. At most two runs go at once, and any can be stopped. Answers stream over the page's existing live connection (`/api/events`), so the review adds no connection of its own. `--review-model` and `--review-effort` (or `WHEELHOUSE_REVIEW_MODEL` and `WHEELHOUSE_REVIEW_EFFORT`) set the defaults, a mid model at low effort; `WHEELHOUSE_REVIEW_CLAUDE` names a different `claude` binary, and `WHEELHOUSE_REVIEW_AGENT=0` turns the agent off (the diff still shows). Like the interviewer, it uses your claude.ai login rather than an API key in the environment unless `WHEELHOUSE_CLAUDE_USE_API_KEY=1`. The cost shown is the CLI's own figure at list price; on a Claude subscription it comes out of your allowance rather than being billed per run.

### Passage steps

| Work  | Steps                                                            |
| ----- | ---------------------------------------------------------------- |
| Ship  | Queued → Building → Checks → Pull request → Your review → Landed |
| Scout | Queued → Scout → Report → Your call → Done                       |

The steps follow Firstmate's delivery mode: direct-PR work has no local Checks step, local-only work has no Pull request step, and with yolo on there is no Your review step because Firstmate merges the work itself. In no-mistakes mode the pipeline opens the pull request before CI runs, so CI checks appear under Pull request. Its CI monitor keeps running until the pull request merges, so an open, non-draft pull request whose checks are green moves to Your review (and **Needs your review**) even while that monitor is still working. Once you ask for changes after it was reported ready, it is the worker's turn and the task starts a new **run**. A change sent from Wheelhouse goes, through Firstmate, to the worker that opened the pull request while that worker is still live, so no second session starts; only when that worker is gone does Firstmate start a new one for the run (see [Messages and retries](architecture.md#messages-and-retries)). Runs are counted the same way either way: run 1 is the first build up to its ready report, and run 2 (then 3, and so on) goes back to the start of the build cycle, Building, then Checks once its validation run starts, then Pull request once it pushes or its CI runs, and Your review when the worker reports the pull request ready again. Cards, On deck, the radar (whose dot moves back to Building) and the task page name the run with its step ("Run 2 · Building"), and the merge call leaves the Decisions inbox until the run is ready. Asking for changes is any of: a review comment on a file or line, a changes-requested review or a commented review that says something, or a comment on the pull request on GitHub that is more than approval or merge chatter (a comment that is only "LGTM", "looks good", "approved", "ship it", "merging after lunch" or emoji does not count; one that adds anything, such as "LGTM once the docs are updated" or a question, does); new commits pushed to it; feedback typed under the live preview, a change asked from Wheelhouse's PR review, or **Fix** / **Request changes** in the Decisions inbox; or a `working:` status line from the worker after the ready report. A plain chat message does not start a run, since it may only be a question; use one of those actions to ask for changes. Wheelhouse keeps the change requests it sent (the latest 2000) apart from the other messages in its message record, so a task's runs do not depend on how many other messages have been sent since. The worker's next ready report ends the run and hands the pull request back to you, whether or not it pushed new commits (it may have only answered a question). Feedback from bots never counts, and neither do replies inside a review thread; the pull request author's own comments count only when the author is the account Wheelhouse reads GitHub as (you reviewing a pull request opened under your account), since otherwise the author is the worker. On the task page, **Stages** starts with the runs (each with how it went: how long it took to build, and how many changes were asked of it); the current run shows the changes that started it as a checklist above its stages (each request with where it came from, its file and line and a link to it on GitHub, ticked once its thread is resolved on GitHub or the worker has reported the pull request ready since), and selecting an earlier run shows its changes, its stages, the validation runs and screenshots from that run, and its times. A card counts the current run's changes ("Run 2: 2 changes to make · 1 done"). These built-in passages are written in the passage file format (`src/lib/server/passages/builtin.ts`), and a project can add steps such as Deployed or Released to them with a [passage file](passages.md).

### Honest gaps

Wheelhouse shows what Firstmate records and says plainly what it cannot see:

- **Deployments** are not recorded by Firstmate. A Deployed (or Released) step, and the watch report's "N live", appear only for projects whose [passage file](passages.md) declares one and the checks that observe it.
- **Preview links** appear only when a worker reports one with a `preview <url>` status line.
- **Decisions** Firstmate holds for you are shown as text, since Firstmate does not record their options; you answer them in the chat or with the **Decisions** inbox's fixed Approve / Fix / Skip choices (see the [README](../README.md#clear-every-open-question-in-one-place)), which go to Firstmate as a message. Questions Firstmate asks with Claude Code's question picker show as buttons.
- **Firstmate's thinking** is not shown as words: Claude Code keeps only a sealed signature for it.
- **Inbox messages** (sent when Firstmate runs in another terminal) report delivery and acknowledgement as a yes/no: Firstmate does not record when it acknowledged a message.
- **Current state** comes from Firstmate's current-state read. Status-log lines are shown as history, never as the current state, and terminal output is a bounded sample, not a transcript.
- **Stale data** is labelled: if Wheelhouse cannot read Firstmate, it keeps the last view and says how old it is.
