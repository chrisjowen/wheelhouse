# Using Wheelhouse

Everything Wheelhouse does, page by page, and how it runs Firstmate. For the short version, see the [README](../README.md).

## Requirements

- Node.js 22 or newer, and npm.
- A Firstmate checkout and its operational home (the directory with `state/` and `data/`). Wheelhouse starts Firstmate's session there when none is running (see [The Firstmate session](#the-firstmate-session)); it never stops or reconfigures Firstmate.
- Whatever Firstmate's own scripts need (bash, python3, git).
- Optional: the GitHub CLI (`gh`), used to read a pull request's state and checks when Firstmate has no cached observation of it, and by the GitHub checks a [passage file](passages.md) declares.
- `tmux` and Claude Code (`claude`) on your `PATH`, to run and talk to Firstmate from Wheelhouse. Without them Wheelhouse says so, still shows a Firstmate session running elsewhere (read-only), and the rest works as usual.

## Use

Run it inside a Firstmate checkout:

```bash
wheelhouse open
```

Or give the paths:

```bash
wheelhouse open --firstmate ~/firstmate --home ~/crew --port 4310
```

| Option                  | Default                                                                                           |
| ----------------------- | ------------------------------------------------------------------------------------------------- |
| `--firstmate <dir>`     | the Firstmate checkout you are in                                                                 |
| `--home <dir>`          | `$FM_HOME`, else the Firstmate directory                                                          |
| `--port <n>`            | `4310`                                                                                            |
| `--state-dir <dir>`     | see below                                                                                         |
| `--config-dir <dir>`    | see [Passage files](passages.md)                                                                  |
| `--tmux-socket <name>`  | `$WHEELHOUSE_TMUX_SOCKET`, else `wheelhouse`; see [The Firstmate session](#the-firstmate-session) |
| `--no-skip-permissions` | start it with `--dangerously-skip-permissions`                                                    |
| `--no-browser`          | open the browser                                                                                  |

`wheelhouse` with no subcommand does the same as `wheelhouse open`.

`--state-dir` is where Wheelhouse keeps its own records: the inbox messages it sent (request ids, bodies, delivery outcomes, receipts and the receipts cursor), one file per Firstmate home, `firstmate/session-start.json`, which its SessionStart hook writes to name the Firstmate session's transcript, and your spec drafts under `specs/` (one JSON file per spec, its screenshots in a folder beside it). It defaults to `$WHEELHOUSE_STATE_DIR`, else `$XDG_STATE_HOME/wheelhouse`, else `~/.local/state/wheelhouse`, and must be outside the Firstmate home.

Wheelhouse checks that Firstmate's integration scripts declare the contracts it understands, starts its server on `127.0.0.1` only, and opens the browser. It answers only requests addressed to `127.0.0.1`, `localhost` or `[::1]`; any other `Host` gets a 421, which blocks DNS-rebinding pages. Every request that changes anything (sending a message, starting the Firstmate session, typing into it, stopping it, answering its questions) must also carry an `Origin` equal to the page's own `http://<host>` origin and this launch's session token, which Wheelhouse issues only to the pages it serves; anything else gets a 403. If the scripts look incompatible it still starts, says so in the UI and in `/api/health`, and shows what it can. Press Ctrl+C to close Wheelhouse; Firstmate and its crew keep running.

## What you see

- **Home** (`/`, the **Firstmate** tab): the conversation with Firstmate, full width, with a rail on the right, **On deck**. See [The Firstmate session](#the-firstmate-session) for the chat. The rail lists, first, **Waiting on you**: a failed step (say, failed checks or a failed deploy) as an urgent card, then pull requests waiting for your review (with their full URLs) and decisions Firstmate is holding for you, in plain words; then **Under way**, then **Up next** and **Landed in the last day**, folded. Every card shows its project as a tag, what it is doing now (in the checks stage, the same step strip and plain line as on Harbour), a small passage with the current step marked, and a badge for anything wrong, each with an icon and words (Checks failed, Stuck, Not responding, Your review, Your call, Addressing your review, Firstmate deciding), and has **Open** (the task page) and **Chat about this** (mentions the task in the message box). A pull request you reviewed after Firstmate reported it ready, and that the worker is reworking, shows under Under way as **Addressing your review** rather than under Waiting on you, until a newer ready report for a newer head. The rail can be resized by dragging its edge (its width is remembered in this browser); on narrow screens the chat stands alone and a button opens the rail as a sheet. The project switcher scopes the rail.
- **Harbour** (`/harbour`): the full board. A one-line watch report, then **Your move** (captain-held decisions and pull requests waiting for your review, each showing its screenshot count, the reported live preview link and the pull request link), **Waiting on Firstmate** (decisions a worker raised that Firstmate is handling), and each project's work as cards. A card names the work (its title without the project prefix), who is doing it (harness, model and worker name) and what they are doing **Now**, in plain words with its age: the latest status line, else the latest line of the worker's console. While the work is in its checks stage (a no-mistakes validation run: rebase, review, tests, docs, lint, push, pull request, CI), a slim strip with one segment per step takes the Now line's place, with one plain line under it, for example "Reviewing the change · 1m 20s · 1 question for Firstmate", "Answer received · fixing review findings, round 2 · 3m" or "All checks passed · CI green". The step under way is drawn solid, a step waiting on Firstmate amber and a failed step red; the line says the same in words. Work under way is led by the worker's live console (a bounded, read-only sample of the last lines, refreshed only while the card is on screen); finished work by its latest screenshot or a picture of the diff. A card with screenshots shows the newest few as small thumbnails of one size that open in the in-page viewer. A card whose worker reported a preview has **Show live preview**, which embeds it in the card with **Open in new tab** and a feedback box (see the task page). A soft pulse on the current step shows a worker that is busy right now, and the card counts the files changed, the questions raised about the work (answered and still open) and the docs and decision records the worker's session referenced, read or changed ("5 docs referenced · 2 changed"; it opens the task's Docs tab). A project switcher (`?project=`) scopes the page, and the **Passage** view (`?view=passage`) puts every task on one chart. An **Under way | Completed** toggle switches the cards between work still in progress (including what needs you) and landed or finished work, newest first (`?view=completed`); **Your move** shows only under Under way.
- **Task page** (`/tasks/<id>`): full width, in two columns. On the left, pinned while you look around, the overview: the task's project and crew, its title and state in plain words, what it is doing now, anything waiting on you or Firstmate (while the work waits on your review, its screenshots, live preview link and pull request link come first here), a small passage, a rough time left, **Live preview** and **Ask Firstmate about this** (opens the home page with the task mentioned in the message box), and its pull request, preview, last check and delivery. Under the overview, for work under way, the worker's **Live terminal** (its live console, which folds away), then the task's time: the work-time estimate (the rough time left jumps to it), where the task's time went and the review questions Firstmate decided on it. On the right, tabs (`?tab=`, kept in the link): **Stages** (the default), **Live preview** (while a worker has reported one), **Conversation**, **Checks**, **Docs**, **Screenshots**, a tab for each plugin section, and **Log**; on narrow screens the overview comes first and the tabs follow. **Stages** is the passage as a vertical list: finished stages fold to one line saying what they came to (say "4 files changed" or "Pull request #13 merged"), the current one is open, later ones are faint, and selecting any stage opens or folds it (**Open all** and **Fold all** do every one). An open stage shows the evidence it produced: files changed, the validation run (under Checks: what is happening now, then a short timeline of what each validation step found or changed and how long it took, with the pull request's CI result on the CI step once the PR is up), the pull request and its CI checks, the report and screenshots. Screenshots show as small thumbnails of one size and open in an in-page viewer (Esc closes, the arrow keys step through them), and selecting a changed file shows its diff against the merge base. Status lines show in plain words, with the raw line behind a small **details** disclosure. **Live preview** embeds a reported preview: only a preview on this machine (`127.0.0.1` or `localhost`) is embedded, in a sandboxed frame, after Wheelhouse has checked that it answers; one that does not answer shows **Preview not running**, and one that refuses to be framed says so, with **Open in new tab** either way. The box under it sends your feedback to the task's worker through Firstmate's inbox, as a note about the task (`Re: <task-id>`) that Firstmate passes on (landed work has no worker, so it has no box). **Full screen** (`&full=1`; Esc closes) puts the page on the left and the feedback on the right: everything sent from this preview, with whether Firstmate has it and any reply, and the box to send more. The feedback sits beside the page, so it never covers what you are commenting on, and **Hide comments** gives the page the full width. **Conversation** is the back-and-forth between the worker and Firstmate, oldest first: each question the worker raised (and each time it was stuck), the automated review's questions with Firstmate's call on each, Firstmate's instructions to the worker, and what you sent Firstmate about the task, each saying who asked, who answered and how it ended (answered, still open, read or not yet read by the worker). **Checks** is what each step of the latest validation run found, in plain words, with what each step did: for tests, how many passed and failed, each failed test with the start of its output (select one to see it), and the scenarios the test step drove; for docs, which documentation changed and what the docs step wrote about it. **Docs** lists the decision records and docs the work changed or the worker's session read; each opens in a readable page in Wheelhouse (`/tasks/<id>/doc?path=`), with a link to the file on GitHub when the project is there. **Log** has the ship's log (history from Firstmate's fleet ledger) and the raw terminal output, which is read-only and sampled only while it is open and the Log tab is showing.
- **Spec** (`/spec`): a guided spec to write before you hand work to Firstmate. Nine short sections, one at a time, each with a one-line prompt and an example: Project (which project, a title and the idea in one sentence), Problem and goal, Who it is for, User journeys, Scope and non-goals, Requirements (each becomes a tick box), UI notes and references (notes, links and screenshots you drop, paste or choose, each with a caption), Constraints and risks, and Open questions. Every section is optional; the outline on the left ticks off the ones you have written, and **Next** and **Back** step through them. Beside it, the live preview shows the spec as a document, following the section you are on, or **As sent**: the one message Firstmate will receive. Drafts save as you type, in Wheelhouse's state directory, and **Your specs** lists them, so you can keep several and come back to any. Once it has a title or a one-sentence summary, **Send to Firstmate** (beside the preview, and at the end of the last section) opens the chat and sends the whole spec there as one message, with a short line asking Firstmate to come back with questions before planning the work; screenshots go as file paths Firstmate can open. It is sent the way the message box sends (typed into the session, or to Firstmate's inbox when it runs elsewhere); if it cannot be sent, the text is left in the message box with the reason. A sent spec is marked **Sent** (or **Edited since sent**) and can be sent again.
- **Logbook** (the **Logbook** tab, which opens on **Headroom**): the session and headroom pages, each with a quiet piece on the home page's rail (the allowance under its headline, an estimate on each card under way, **Decided for you** with the latest three calls, and **Where time went today**) and a page of its own:
  - **Decided for you** (`/decisions`): review questions the automated review raised that Firstmate answered on your behalf, newest first, grouped by day and filterable (Fix it, Keep as is, Defer). Each opens to show the question, Firstmate's call and its reason (the reviewer's full note is folded away), whether the work has landed, **I'd decide differently** (opens the chat with the task mentioned and a draft to finish) and **Chat about this**. Questions that carry your own words (prototype reviews and other captain calls) are never listed.
  - **Where time went** (`/time`): for today, the last 7 or 30 days, each task's time split into building, automated review and fixes, Firstmate deciding, CI checks and waiting on you, on one shared scale, with per-project totals and how long work usually takes from start to ready for you.
  - **Headroom** (`/headroom`): how much of your Claude allowance is left, when each window resets and whether the recent pace lasts until then; who on this machine is using Claude (Firstmate, each task with its share of automated review, other use) over the last 5 hours or 7 days; and use per hour for the last day. When a window will run out before it resets, a warning shows in the header on every page. **Ask Firstmate to hold new work** drafts that message in the chat. If quota-axi needs its one-time Keychain approval, the page and the rail say **Connect your Claude usage** and give the command (`quota-axi --allow-keychain-prompt`) to run once yourself; Wheelhouse never asks for that approval.
- **Work-time estimate**: work under way shows a rough estimate of the work time left before it is ready for your review ("About 20 min left · rough guide"), on its rail and Harbour cards and, with the steps still ahead, on its task page; "Taking longer than usual" when similar work had finished by now; prototypes and scouting show their time under way with "no set end". It is worked out from finished work of the same kind (this project's when it has at least three, else across projects): what similar work still had left at the same point, as a median with a 25th–75th percentile range, labelled an early guess, a rough guide or a good guide by how much history there is and how much it agreed. The task page also shows where the task's time went and the review questions Firstmate decided on it.
- **Project passage** (`/projects/<id>/passage`, linked from each project's header): the steps and checks the project's passage declares, where each came from, and any problem with its passage files, plus the switches that enable a project file's network checks and allow the passage's command checks, each listing exactly what it turns on. **Edit passage** opens the passage editor (`/projects/<id>/passage/edit`): see [Editing a passage in Wheelhouse](passages.md#editing-a-passage-in-wheelhouse).

- **Plugins** add to fixed places on these pages: a project tab (linked beside a project's name and on its scoped Harbour view, each its own full-window page at `/projects/<id>/<plugin>/<tab>`), a card in the project's Harbour section, a section on the task page, evidence under one passage step, and a card under a Firstmate reply in the chat that links something the plugin knows. Wheelhouse ships two: **Project links** (off unless turned on in `plugins.json`): a project's repository, README and pull requests, the task's branch, and a compare link under the Pull request step; and **Docket** (on for projects with a `.docket.yaml`): a read-only chart of the project's docket. See [Plugins](plugins.md).

Everything you type goes to Firstmate. There is no way to message a worker directly and no worker controls anywhere. Wheelhouse writes nothing into the Firstmate home, except a project's `.wheelhouse.yaml` in its clone when you save it in the passage editor; it types into the Firstmate session it runs, and sends to a session running elsewhere only through `fm-inbox.sh note`.

### The Firstmate session

`wheelhouse open` starts the one Firstmate session when none is running: an ordinary interactive `claude` in Firstmate's checkout, inside a detached tmux session named `wh-firstmate` on Wheelhouse's own tmux server (`tmux -L wheelhouse`; change the name with `--tmux-socket <name>` or `WHEELHOUSE_TMUX_SOCKET`), never the default server the crew run on. It is the same session you would start in a terminal, so Firstmate's own hooks and supervision run unchanged.

- **One session only.** Firstmate's session lock decides: when `fm-inbox.sh ready` says another session holds it (say, Firstmate running in your own terminal), Wheelhouse starts nothing and shows that session's conversation read-only, since it cannot type into a terminal it does not own; the message box then sends to Firstmate's inbox (`fm-inbox.sh note`, see [Messages and retries](architecture.md#messages-and-retries)), and Firstmate's reply appears in the conversation. If the lock cannot be read, it starts nothing either. If starting fails, **Start Firstmate here** on the home page tries again, under the same rule.
- **It outlives Wheelhouse.** The session belongs to tmux, so closing the browser or Wheelhouse leaves it running, and the next `wheelhouse open` shows it again. To use your own terminal, run `tmux -L wheelhouse attach -t wh-firstmate`.
- **Permissions.** It starts with `--dangerously-skip-permissions` (and Claude Code's bypass-mode confirmation skipped), so Firstmate runs without stopping to ask; `--no-skip-permissions` starts it without, and Claude Code's permission prompts then appear in the terminal drawer. Before starting it, Wheelhouse pre-approves Claude Code's workspace trust for Firstmate's checkout (`hasTrustDialogAccepted` in `${CLAUDE_CONFIG_DIR:-$HOME}/.claude.json`, written atomically; no other setting is touched). `FM_HOME` is passed when the home differs from the checkout.
- **Its transcript.** Wheelhouse adds one SessionStart hook of its own through `claude --settings` (merged with Firstmate's hooks, never replacing them), which writes the hook's input, including `transcript_path`, to `<state-dir>/firstmate/session-start.json`. The chat follows that file, and finds the new one after `/clear`, `/compact` or a restart. For a session it did not start, it looks up the Claude session id Firstmate records beside its lock (`state/.lock-session`), else the newest transcript whose records name Firstmate's checkout. It only ever reads the transcript, and reads at most its last 8 MiB when first opening it (earlier messages stay in the terminal).

The chat shows the captain's messages (including ones typed while Firstmate was busy), Firstmate's replies as Markdown, and its work between replies folded into one line ("3 commands, 1 skill"; "Thought for 7s") that opens to a row per step and then to the step's input and result. Claude Code records only a sealed signature for its thinking, so thinking shows as how long it took, not the words. A turn started by a background wake (a task notification) whose reply is empty or only an all-clear such as "Captain, shipshape." is kept out of the chat; the **ship health** pill in the chat's bar (All well, N need you, Keeping an eye on a problem, Something failed) says when the last background check ran, or that one is running, and lists recent ones. A wake with something to say reads as an ordinary message. Slash commands and their output show as they do in the terminal.

- **Typing.** Enter sends, Shift+Enter adds a line. The message is pasted into the session as one bracketed paste (`tmux load-buffer` and `paste-buffer -p`), then Enter, so a multi-line message never submits early. `/` at the start offers Firstmate's commands (its skills marked `user-invocable: true` and its `.claude/commands`) and the Claude Code built-ins that work from a chat (`/compact`, `/clear`, `/context`); built-ins that open a picker in the terminal are left out. `#` anywhere offers tasks and pull requests and inserts a chip, which Firstmate receives as `[task <id>: <title>]` (or `[PR <url> — task <id>: <title>]`), the task id being the key its own scripts use. While Firstmate works, an empty message box offers **Stop**, which presses Escape in the session.
- **Questions.** When Firstmate asks with Claude Code's question picker, the chat shows the question with its options as buttons; picking sends the keys the picker expects, worked out on the server from the open question. Free-text answers go through the terminal.
- **The terminal drawer** shows the session's own screen, live, for anything the chat cannot show. It is a WebSocket at `/api/firstmate/terminal`, served on `127.0.0.1` only, backed by a real pty (`node-pty`) running `tmux -L <socket> attach-session -t =wh-firstmate`.

Everything that types into the session (sending, Stop, answering, the terminal) is refused unless its `Host` is loopback, its `Origin` is the page's own and it carries this launch's session token (as a WebSocket subprotocol for the terminal), and it reaches only `wh-firstmate` on Wheelhouse's own tmux server, and only when Wheelhouse runs it.

### Passage steps

| Work  | Steps                                                            |
| ----- | ---------------------------------------------------------------- |
| Ship  | Queued → Building → Checks → Pull request → Your review → Landed |
| Scout | Queued → Scout → Report → Your call → Done                       |

The steps follow Firstmate's delivery mode: direct-PR work has no local Checks step, local-only work has no Pull request step, and with yolo on there is no Your review step because Firstmate merges the work itself. In no-mistakes mode the pipeline opens the pull request before CI runs, so CI checks appear under Pull request. Its CI monitor keeps running until the pull request merges, so an open, non-draft pull request whose checks are green moves to Your review (and **Needs your review**) even while that monitor is still working. If the pull request then gets review comments, a changes-requested review or new commits after it was reported ready, the work is **Addressing your review** (under way) until a newer ready report for a newer head. Only review feedback from people other than the pull request's author counts, and never from bots: this assumes workers and Firstmate open pull requests as their own account, not the one you review with. These built-in passages are written in the passage file format (`src/lib/server/passages/builtin.ts`), and a project can add steps such as Deployed or Released to them with a [passage file](passages.md).

### Honest gaps

Wheelhouse shows what Firstmate records and says plainly what it cannot see:

- **Deployments** are not recorded by Firstmate. A Deployed (or Released) step, and the watch report's "N live", appear only for projects whose [passage file](passages.md) declares one and the checks that observe it.
- **Preview links** appear only when a worker reports one with a `preview <url>` status line.
- **Decisions** Firstmate holds for you are shown as text, since Firstmate does not record their options; you answer them in the chat. Questions Firstmate asks with Claude Code's question picker show as buttons.
- **Firstmate's thinking** is not shown as words: Claude Code keeps only a sealed signature for it.
- **Inbox messages** (sent when Firstmate runs in another terminal) report delivery and acknowledgement as a yes/no: Firstmate does not record when it acknowledged a message.
- **Current state** comes from Firstmate's current-state read. Status-log lines are shown as history, never as the current state, and terminal output is a bounded sample, not a transcript.
- **Stale data** is labelled: if Wheelhouse cannot read Firstmate, it keeps the last view and says how old it is.
