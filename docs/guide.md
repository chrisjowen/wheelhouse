# Using Wheelhouse

Everything Wheelhouse does, page by page, and how it runs Firstmate. For the short version, see the [README](../README.md).

## Requirements

- Node.js 22 or newer, and npm.
- A Firstmate checkout and its operational home (the directory with `state/` and `data/`); without one, `wheelhouse open` opens the [setup wizard](#setting-up-firstmate), which clones it. Wheelhouse starts Firstmate's session there when none is running (see [The Firstmate session](#the-firstmate-session)); it never stops or reconfigures Firstmate.
- Whatever Firstmate's own scripts need (bash, python3, git).
- Optional: the GitHub CLI (`gh`), used to read a pull request's state and checks when Firstmate has no cached observation of it, and by the GitHub checks a [passage file](passages.md) declares.
- `tmux` and Claude Code (`claude`) on your `PATH`, to run and talk to Firstmate from Wheelhouse. Without them Wheelhouse says so, still shows a Firstmate session running elsewhere (read-only), and the rest works as usual.

## Use

Run it inside a Firstmate checkout, or anywhere once the [setup wizard](#setting-up-firstmate) has set one up:

```bash
wheelhouse open
```

Or give the paths:

```bash
wheelhouse open --firstmate ~/firstmate --home ~/crew --port 4310
```

| Option                  | Default                                                                                           |
| ----------------------- | ------------------------------------------------------------------------------------------------- |
| `--firstmate <dir>`     | the Firstmate checkout you are in, else the one the setup wizard remembered                       |
| `--home <dir>`          | `$FM_HOME`, else the home the setup wizard remembered, else the Firstmate directory               |
| `--port <n>`            | `4310`                                                                                            |
| `--state-dir <dir>`     | see below                                                                                         |
| `--config-dir <dir>`    | see [Passage files](passages.md)                                                                  |
| `--tmux-socket <name>`  | `$WHEELHOUSE_TMUX_SOCKET`, else `wheelhouse`; see [The Firstmate session](#the-firstmate-session) |
| `--no-skip-permissions` | start it with `--dangerously-skip-permissions`                                                    |
| `--no-browser`          | open the browser                                                                                  |

`wheelhouse` with no subcommand does the same as `wheelhouse open`.

`--state-dir` is where Wheelhouse keeps its own records: the inbox messages it sent (request ids, bodies, delivery outcomes, receipts and the receipts cursor), one file per Firstmate home, `firstmate/session-start.json`, which its SessionStart hook writes to name the Firstmate session's transcript, and the [messaging gateway](#the-messaging-gateway)'s record beside the home's messages (`gateway.json`) and its audit log (`gateway/discord.jsonl`), and the files you attach in the chat (`uploads/`, kept seven days; see [The Firstmate session](#the-firstmate-session)). It defaults to `$WHEELHOUSE_STATE_DIR`, else `$XDG_STATE_HOME/wheelhouse`, else `~/.local/state/wheelhouse`, and must be outside the Firstmate home.

Wheelhouse checks that Firstmate's integration scripts declare the contracts it understands, starts its server on `127.0.0.1` only, and opens the browser. It answers only requests addressed to `127.0.0.1`, `localhost` or `[::1]`; any other `Host` gets a 421, which blocks DNS-rebinding pages.
Every request that changes anything (sending a message, attaching a file, starting the Firstmate session, typing into it, stopping it, answering its questions) must also carry an `Origin` equal to the page's own `http://<host>` origin and this launch's session token, which Wheelhouse issues only to the pages it serves; anything else gets a 403. A `*.localhost` name is the one exception to the loopback `Host` rule: while a plugin's [host route](plugins.md#host-routes-and-address-rewrites) answers it, Wheelhouse hands its requests to that plugin, checking only that a change or WebSocket carries that name's own `Origin`, not the session token. If the scripts look incompatible it still starts, says so in the UI and in `/api/health`, and shows what it can. Press Ctrl+C to close Wheelhouse; Firstmate and its crew keep running.

### Setting up Firstmate

When `wheelhouse open` finds no Firstmate (none given with `--firstmate`, none above the folder it runs in, none remembered), it starts anyway and every page opens the setup wizard (`/setup`) instead. The wizard answers only a browser on this computer, never one reaching Wheelhouse through Wheelhouse Cloud, and each change it makes carries the page's session token like every other. Run it again any time from **Settings → Setup**. Its steps:

1. **Where Firstmate lives.** Clone the public [Firstmate repository](https://github.com/kunchenguid/firstmate) to a folder (`~/firstmate` by default), or use a Firstmate checkout already on this computer (the wizard lists any it finds: first the one above the folder Wheelhouse runs in, which it would pick over any other, then the usual places). It clones only into a folder that does not exist yet or is empty, and never overwrites, moves or deletes anything already there: a folder with files in it, a file or a link is refused. Wheelhouse remembers the choice in `firstmate.json` in its config directory, so `wheelhouse open` finds it from any folder; `--firstmate`, the checkout you run it in and `$FM_HOME` still win. A Wheelhouse started for a given Firstmate (with `--firstmate`, or inside a checkout) shows it and does not switch from the page.
2. **Tools Firstmate needs.** The wizard runs Firstmate's own bootstrap check (`bin/fm-bootstrap.sh`, detect-only, so it changes nothing) and lists what it checks: git, gh and whether you are signed in, node, the runtime backend's tools (tmux and treehouse for the default tmux backend, Herdr's for Herdr), no-mistakes, the axi tools, and tmux, which Wheelhouse runs the session in. Each has a tick or what is wrong, with the version it found. A tool whose install is exactly `npm install -g <package>` (where npm's global folder needs no sudo) or `brew install <package>` (where Homebrew is installed), optionally followed by the package's own `setup hooks`, has **Install**: it shows the exact command and runs it, without a shell, only when you click **Run it**. Everything else (installers piped to `sh`, anything with `sudo`, `gh auth login`) is a command to copy into your own terminal, adapted to this computer's package manager (Homebrew, apt, dnf or pacman), with a link to the tool's own instructions. Wheelhouse never reads, stores or prints a token.
3. **Claude Code.** Missing, it installs with `npm install -g @anthropic-ai/claude-code` (shown first, run on your click; Anthropic's own installer is offered for your terminal), then checks the version `claude --version` reports. **Sign in to Claude Code** opens Claude Code itself in a terminal on the page, where you sign in and accept its terms with your own keys, as in any terminal; Wheelhouse never answers its prompts or writes its settings for you, and keeps nothing you type or it shows. The terminal runs in a folder of Wheelhouse's own (in its state directory), not in Firstmate's, and closes when the step ends. Type `/exit` and the wizard tests it: `claude -p` asked for one word, a tick once it answers.
4. **Firstmate's own checks.** Its bootstrap check again, its readiness check (`fm-inbox.sh ready`), and Wheelhouse's: that it can read this Firstmate's scripts, that the home can be written and holds none of Wheelhouse's own folders, that tmux is here and Claude Code answers.
5. **Plugins.** The plugins bundled with Wheelhouse, each with a switch that turns it on or off for every project (as **Settings → Plugins** does, in `plugins.json`), and suggested ones to install from GitHub (docket's and improve's), each reviewed in the usual install dialog before anything is kept.
6. **Start Firstmate.** Once Claude Code answers and tmux is here, **Start Firstmate** starts the session (never a second one) and shows its terminal, for anything Claude Code asks the first time, such as trusting the Firstmate folder or accepting its permissions mode; **Open the Firstmate chat** goes to the home page.

### Wheelhouse in Docker or on another computer

The crew reports addresses on Wheelhouse's own computer: live previews, links in Firstmate's replies, status notes and decision cards, such as `http://localhost:5173/`. When you open Wheelhouse from somewhere else (it runs in a Docker container, a cloud workspace or another computer, and you reach it through a forwarded port), those addresses point at your own computer, where nothing answers. Install the [Localhost proxy](https://github.com/chrisjowen/localhost-proxy-wheelhouse) plugin and turn it on in **Settings → Plugins**: it shows each such address through Wheelhouse itself, so `http://localhost:5173/` opens as `http://5173.localhost:4310/`, where 4310 is the port you reached Wheelhouse on, and only that port needs forwarding. It uses Wheelhouse's [host routes and address rewrites](plugins.md#host-routes-and-address-rewrites); without such a plugin, nothing changes.

### Wheelhouse Cloud

Wheelhouse Cloud lets you use the Wheelhouse on your own machine from any browser, through a hosted gateway you have an account on. Wheelhouse, Firstmate and the crew keep running on your machine; the gateway signs you in and carries the connection, which your machine opens to it (one outbound TLS WebSocket), so Wheelhouse still listens on `127.0.0.1` only and no port is opened.

**Remote access is off until you start it.** `wheelhouse open` never connects by itself, not even for a machine that is already paired: the pairing is kept, disconnected, until you press **Start** on the **Remotes** page (the fourth item in the left menu). A Start you leave on is remembered in the settings, so it resumes when Wheelhouse opens again, until you press **Stop**.

1. Open **Remotes** and check the gateway. It is `https://cloud.chrisjowen.net` unless you name another; anyone can host a gateway, so point it at your own if you run one (an `https://` address, or `http://` on this computer for testing). It can be changed while the machine is not paired, here or in **Settings → Cloud**; clear the field to go back to the default.
2. Press **Start**. A machine that is not paired yet is paired first: Wheelhouse makes a key for this machine and shows a short code, the gateway's own pair page to type it at, and the key's fingerprint, with a warning.
3. On a device you trust, open that address yourself, sign in, type the code, check that it names the machine you expect, pick this machine's fingerprint from the ones it shows, and approve. Type the code yourself: whoever approves it can use this Wheelhouse, terminals included, so they can run commands on the machine. If someone asked you for the code, press **Stop**.
4. Once approved, remote access starts: the running `wheelhouse open` connects within seconds and keeps the connection up, through server restarts too. On the gateway, open the machine. Its pages, terminals and live previews work as they do here; previews open on the gateway's host for their port.

- **Only on this machine.** The Remotes page, **Settings → Cloud** and their API answer only a browser on this computer: a session through the gateway cannot read a pairing code, change the gateway, pair the machine again, or start and stop the connection.
- **The key** is an Ed25519 key made on the machine; it never leaves it and is never shown. It is kept in the macOS Keychain (service `wheelhouse-cloud`, account `device:<digest of the cloud directory>`), else alone in `<config-dir>/cloud/device.key`, readable by your user only. The gateway keeps only the public key.
- **What the connector refuses.** Requests reach only this Wheelhouse and the ports it reports as previews (task previews, and forwarded second-mate previews), never Wheelhouse's own restart, and nothing while remote access is stopped here. Wheelhouse's own checks still apply: the connector sets the loopback `Host` and, for a change, the page's `Origin` the gateway has checked, and the session token works as it does locally.
- **What you see here.** **Remotes** shows whether the machine is online, since when, when the gateway was last heard from, and the sessions it has relayed (who, how many requests, when: never what was sent), with **Stop** (which disconnects them all) and **Revoke**, which removes the machine on the gateway and deletes its key here. Removing the machine on the gateway closes the connection, deletes the key here too and stops remote access until you press **Start** again.
- **What the gateway sees.** It decrypts the traffic it relays, in memory: someone who controls the gateway could read it and send requests into the sessions you open. Stop remote access when you do not need it.
- **On a phone.** Wheelhouse fits a phone's screen: a tab bar at the foot, pickers that rise from the bottom as sheets, and previews full screen with **Share for review** in a dock in reach of your thumb (see [Live previews](#the-firstmate-session)). Add the machine's page to the home screen (Safari's Share → **Add to Home Screen**, or Chrome's **Install app**) and it opens as an app of its own, with Wheelhouse's anchor as its icon.

The same can be done from a terminal, for a machine you set up by hand or one where Wheelhouse runs under another supervisor. Pairing there (`connect`) or turning the cloud on there does not start remote access for `wheelhouse open`; `run` keeps a connection up itself, for as long as it runs.

| Command                        | Does                                                                                                                                                                |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `wheelhouse remote connect`    | Pair this machine (`--gateway <url>`, remembered, default `https://cloud.chrisjowen.net` or the one set; `--name <name>`, default its host name)                    |
| `wheelhouse remote status`     | On or off, started or not, the gateway, the machine and its fingerprint, the connection, last seen and relay sessions                                               |
| `wheelhouse remote off` / `on` | Turn the cloud off (the connection closes and nothing is relayed; the pairing is kept) or on again (`run` may connect; `wheelhouse open` still waits for **Start**) |
| `wheelhouse remote disconnect` | Revoke the machine on its gateway and delete its key here (the key is deleted even if the gateway is down)                                                          |
| `wheelhouse remote run`        | Keep the connection up now, without **Start** (`--port <n>`, default 4310), pairing first when not paired (`--gateway <url>`, `--name <name>`)                      |

Each takes `--config-dir <dir>`; the settings are in `<config-dir>/cloud/settings.json` (`started` is the Remotes page's Start, `gateway` is empty for the default), and a running Wheelhouse picks up a change within a few seconds.

### Keeping Wheelhouse up to date

When Wheelhouse runs from a git clone (the installed `wheelhouse` linked to a checkout, as in [Developing Wheelhouse](development.md)), it can upgrade itself. The arrow-up icon in the header, beside the bell, is its version and updates: it checks the default branch of the clone's `origin` on GitHub when a page asks and the last check is more than six hours old, or at once from **Check now**, and changes nothing but the fetched branch. While Wheelhouse is up to date the icon stays quiet; when the branch has newer commits it becomes an outlined **Update** button, whose menu lists them (with the new version when `package.json` changed, and **Compare on GitHub**), says what a restart would stop, and offers **Upgrade and restart**. That fast-forwards the clone to the new commit, runs `npm ci` and `npm run build`, and restarts Wheelhouse's server through the same watcher that restarts it after a crash, showing each step; the page reconnects by itself and says it upgraded. Firstmate and its crew keep running.

It never resets, stashes, merges or rebases. A clone with local changes to tracked files (it lists them), on another branch or a detached HEAD, or with commits of its own that the default branch lacks is refused with the reason, and nothing is changed; a small amber dot on the icon marks it. The install and build run in the directory the server runs from, so pages may briefly misbehave while an upgrade builds. A failed `npm ci` or build leaves the clone at the new commit with an incomplete build and shows the end of the output; fix it and rebuild (`npm ci && npm run build`) before Wheelhouse restarts, or it restarts from the broken build. Installed from npm, Wheelhouse is not a clone and says so: update it with `npm install -g @chrisjowen/wheelhouse`. Upgrading from a page needs the server to have been started by `wheelhouse open`, which can restart it.

`wheelhouse upgrade` does the same from a terminal: it lists what is new, asks, upgrades with npm's output shown, then restarts every running Wheelhouse that loads plugins from the same directory (asking first when one has a service launch in progress). `--check` only says whether there is something new; `--yes` upgrades and restarts without asking.

If Wheelhouse's server dies (a crash, or a process killed outright), a small watcher in `wheelhouse open` restarts it on the same port, up to five times within a minute; if it dies again within that minute, Wheelhouse gives up and closes. The watcher is about Wheelhouse only: it never starts, stops or restarts Firstmate or its crew, and a restarted server does not start a Firstmate session (start one from the home page if you need it). Open pages say plainly when they have lost the server, keep trying, and pick up again on their own once it answers, reloading their data when the server was restarted.

## What you see

Wheelhouse wears one look, light or dark: near-black navy at night and warm paper by day, gold for anything that needs you, teal for what is going well and blue for Firstmate at work, with labels in letter-spaced mono capitals and page titles in a serif.

The menu down the left, under **Bridge**, carries the main sections (Firstmate, Harbour, Decisions, Remotes, Logbook, then any plugin's own page, such as **Improvements**), each with an icon: Firstmate marked **Working** while Wheelhouse's own Firstmate session is mid-turn, the Harbour with a count of the work in play, Decisions with a count of open questions, and a plugin's page with the count it reports, if any. Under **Second mates** it lists every second mate Firstmate runs: an initials disc, its name, where it runs (its host, or this computer) and a status dot (green online, gold when one of its questions waits on you, grey when quiet or unread, red when it cannot be read), each opening its section of the Second mates page. It folds to its icons (with their names as tooltips) from its **Collapse** button or Cmd/Ctrl+B, and this browser remembers which you chose; on a narrow screen it is left out and the sections sit in the header instead. The header carries the logo with the name of the Firstmate home Wheelhouse watches (its folder's name, with the full path on hover), whether Firstmate is on watch, the project switcher, Wheelhouse's version and updates (see [Keeping Wheelhouse up to date](#keeping-wheelhouse-up-to-date)), the [ship's bell](#the-ships-bell), **Settings** (the gear: the [messaging gateway](#the-messaging-gateway) and **Plugins**) and the light/dark switch. Each section keeps its own pages in a row of tabs at its top (the Harbour's **Projects**, **Passage** and **Radar** views, and a project's own pages under its banner; the Logbook's pages, then **Plugins**, which opens Settings → Plugins). The switcher lists your projects, each with how many things need you: All projects, the ones you pinned, then the most active (waiting on you, under way, latest activity), six in all, then the rest, with a search box that has the keyboard (arrow keys move, Enter picks, Esc closes); choosing a project scopes the page (on the Harbour and a project's pages, it opens that project's page). Projects whose names share a leading part (split on `-`, `_` or `/`) with another project sit under it as a heading, each shown by its own part: `ai-innovations-chat-agent` and `ai-innovations-workflow` read as **chat-agent** and **workflow** under **ai-innovations**, with the full name on hover; one shown on its own reads "ai-innovations › chat-agent", the prefix giving way first. Each project has a two-letter tile from that part (CA, WO) in one of a few quiet colours, so siblings look different. Each row pins or unpins it and renames it: a friendly name, kept in this browser, replaces the shown name everywhere the project is listed and is found by search along with the full name (clear it to go back to the full name).

- **Home** (`/`, the **Firstmate** tab): the conversation with Firstmate, full width, with a rail beside it, **On deck**, on the left by default; the button with two arrows in the chat's bar moves it to the other side, and this browser remembers which. See [The Firstmate session](#the-firstmate-session) for the chat. On deck's title reads "On _deck_". Under it, two gauges: Claude's headroom this week (what is left of the weekly allowance until it resets, linking to Headroom) and **Checks** (how much of the work in play has nothing failing, and how many are failing, linking to the Harbour). On deck shows every piece of work as a line of two rows: what it is (or, for a question, the question), then its project tag (its short or friendly name, as in the project list), what it is doing now and how long ago it last moved (`18m`, `2h`), with its state as a mono tag on the right (Checks failed, Stuck, Not responding, Your review, Your merge, With reviewers, Your call, Run 2 · Building and the like, Firstmate deciding, Working, Queued) and **Chat about this** (mentions the task in the message box) at the end of the line on hover or focus. Selecting a line opens it in place, and selecting it again folds it: a task shows what its card used to (its badge, the second mate and host it runs on, what it is doing now, or in the checks stage the same step strip and plain line as on a project's page, a small passage with the current step marked, the rough time left, its pull request's full URL, **Open live preview**, which opens the preview in place, **Open**, the task's page, and **Chat about this**); a question shows the same decision box as the Decisions page (Firstmate's recommendation, **Chat about this**, **Agree**, **Ask me later**, and the evidence). The up and down arrow keys move between lines, and Home and End jump to the first and last. The lines are grouped by whose crew runs the work: Firstmate's own first, then each second mate Firstmate runs, under a heading with its name and where it runs (its host, or this computer), and its health when it is not plainly online; a second mate's work sits beside your own crew's, while the second mates themselves are never lines (see [Second mates](#second-mates)). When Firstmate runs any second mates, a row of pills under the gauges picks whose work it shows: **All**, **Firstmate**, then one per second mate (a suffix every second mate's name shares, such as `-mate`, is left off there; the headings keep the full name), each with a count of its work in play, or, in gold, of what in it waits on you. The left and right arrow keys move along it, selecting a heading picks that crew too, and this browser remembers the choice. With one second mate picked, its heading also says its state, its queue and its last report, with **More** linking to its section of the Second mates page. Claude headroom also sits in the rail's header (what is left of the 5-hour and weekly allowances, the weekly one in gold, the one that may run out before it resets in amber), linking to Headroom. Under it, the rail shows one list at a time, in tabs that each carry a count for the crew shown (the tab you pick is remembered in this browser): **Under way** (the default: work in progress and green pull requests waiting on other people's review; what waits on a decision is under Needs you, and work that landed or whose pull request was closed without merging drops off by itself), with **Up next** folded behind a button that adds the queued work to each crew's lines; **Needs you**: every question Firstmate escalated to you from **Decisions** (work Firstmate is holding for you, and a green pull request whose merge call is there, shows as that question, not twice), then a failed step (say, failed checks or a failed deploy), then pull requests waiting for your review or merge and other calls, then workers' questions Firstmate is handling, which it brings to you if they need you, then **Decided for you** with **See all**; **Landed** in the last day, then where today's crew time went; and a tab for each plugin card, such as **Harness**. A pull request you asked to change after it was reported ready starts a new run (the change goes to the worker that opened it while that worker is still live, and Firstmate starts a new session only once it is gone) and shows under Under way (say **Run 2 · Building**) rather than under Needs you, until the worker reports it ready again (see [Passage steps](#passage-steps)). Under the list, **Open every project in Harbour** and, with second mates, **Every second mate…** lead on, and **Harbour at a glance** lists the busiest projects (up to four) with one word for where each stands (Needs you, Working, Quiet) and a bar for how much of its work has landed. The rail can be resized by dragging its edge (its width is remembered in this browser; a double click restores the default); on narrow screens the chat stands alone and a button opens the rail as a sheet. The project switcher scopes the rail, and its crew toggle then offers only the second mates with work in that project.
- **Harbour** (`/harbour`): every project Firstmate looks after, at a glance. A one-line watch report counts the projects, what needs you, what is under way (and how much of it is held up) and what landed this week. The **Projects** view opens with **The fleet**, a compact chart of what is moving across every project: a line per project with work on it (most pressing first), each task a small vessel at its lane (Queued, Building, Testing, Pull request, Landed, as on the Radar). A filled vessel is working right now and a hollow one is under way but idle; amber is waiting on you, a red diamond is held up and green has landed (in the last day, fading after the first hour); a dashed brass ring marks work on a second mate, whose ship also follows the project's name. Only what waits on you or is held up carries its name (one per line); every other vessel names itself on hover or focus. A faint wake runs along each line to its furthest open work, and a lane with more than four vessels folds the rest into **+n**. Nothing moves until something changes: a vessel glides to its new lane as the live fleet read changes and sends out one soft ring when it lands. A vessel opens its task's page, and a project's name (or a **+n**) opens the project's page. Below it, the view gives each project with something open a card, most pressing first (needs you, then held up, then new, then under way, the latest activity first), and each card answers, top to bottom: the project's state in one word, with an icon (**Needs you**, **Held up**, **New** for a project whose first work is from the last two weeks and that has finished nothing yet, **Under way** or **Quiet**); the first thing waiting on you (a review, a merge or a decision, in plain words, and how many more), else the first piece of stuck work (blocked, failed, out of contact or at a failed step) or a passage file with problems, each with how long it has been that way, counted from its latest status line or validation run, else from when it started ("Waiting for 3 h", "Held up for 2 days"; left out when nothing says); up to three pieces of work under way, each with a short tick per passage step and the step it is on, then how many more and how many are queued; how much landed this week and the latest; and, along its foot, two weeks of activity (a bar a day, as tall as that day's commits on any branch of the project's clone, read with git and kept ten minutes; a dark bar is a day something landed), its open pull requests and when anything last happened. A click anywhere on a card opens the project's page; the lines inside it open the task they name. Second mates follow, a line each (whether it is online, its state, how much it has in flight and queued, what waits on you and its projects), opening its place on the Second mates page. Projects with nothing open fold into **Quiet waters** underneath, a line each with when something last landed and the same activity bars. An **All | Needs you | Held up | Under way | Quiet** toggle (`?show=`), each with its count, narrows the cards (new projects show under Under way). The **Passage** view (`?view=passage`) puts every task on one chart. The **Radar** view (`?view=radar`) is the fleet as it moves: one dot per task in five lanes (Queued, Building, Testing, Pull request, Landed), placed by the task's current passage step (a step a passage file adds sits in the lane of the built-in step before it). A dot pulses while its worker is busy, turns amber when it is waiting on you and red (a diamond) when it is stuck: blocked, failed, out of contact or at a failed step; a hollow dot is idle, a brass ring is with Firstmate. Dots glide to their new lane as the live fleet read changes (over the page's one existing event stream), and the line above the lanes counts them by state. Landed dots stay for a day, fading after the first hour. Hover, focus or tap a dot for its card: the project, the task, its current step, how long it has been in its lane and, once the page has seen it change step, in that step, and what it is doing, with a link to the task. Time in the lane counts from when the page saw the task move there, else from Firstmate's records (when its validation run started, when it landed); a status line or the date the task was filed is not a move, and where nothing says, it shows as unknown. Under reduced motion nothing glides or pulses. The project switcher scopes the Passage and Radar views (`?project=`); on the Projects view it opens the project's page. An address from before Projects and the Harbour were one page still works: `/projects` opens the Harbour, and `/harbour?project=<id>` the project's page.
- **A project's page** (`/projects/<id>`, from its card on the Harbour or the project switcher): a banner with the project's tile, name and state, its description, the one thing that matters most right now in a sentence (what waits on you or what is stuck, and for how long, what is moving, or when it last landed), and how much is under way, waiting on you and landed this week, when anything last happened and how it ships (for example "Full checks for product work · Firstmate merges"); then a row of tabs for all of the project's pages: **Work**, each plugin's tab (such as **Issues**, **Secrets** or a docket **Chart**), **Passage** (in red when its passage file has problems) and its **Repository** (from the clone's `origin` remote, GitHub-style remotes only). Every one of the project's pages keeps the banner; a plugin tab, which fills the window, keeps it as one line. **Work** is the project's board: **Your move** (captain-held decisions and pull requests waiting for your review, each showing its screenshot count, the reported live preview link and the pull request link), **Waiting on Firstmate** (decisions a worker raised that Firstmate is handling), **Waiting on reviewers** (green pull requests whose review or approval other people owe, so there is nothing for you to do yet), the project's plugin cards, then its work under way as cards and what is queued next. A card names the work (its title without the project prefix), who is doing it (harness, model and worker name) and what they are doing **Now**, in plain words with its age: the latest status line, else the latest line of the worker's console. While the work is in its checks stage (a no-mistakes validation run: rebase, review, tests, docs, lint, push, pull request, CI), a slim strip with one segment per step takes the Now line's place, with one plain line under it, for example "Reviewing the change · 1m 20s · 1 question for Firstmate", "Answer received · fixing review findings, round 2 · 3m" or "All checks passed · CI green". The step under way is drawn solid, a step waiting on Firstmate amber and a failed step red; the line says the same in words. Work under way is led by the worker's live console (a bounded, read-only sample of the last lines, refreshed every 2 seconds, only while the card is on screen; select it to open it in the browser's full screen, where the worker's screen is drawn large enough to fill it, refreshes every second and stays where you scrolled to, and Esc or the close button returns to the page); finished work by its latest screenshot or a picture of the diff. A card with screenshots shows the newest few as small thumbnails of one size that open in the in-page viewer. A card whose worker reported a preview has **Open live preview**, which opens it in place, growing out of the card: full size, with the preview helper beside it to talk it through and send feedback, as in the task page's **Full screen**; Esc or **Close** shrinks it back into the card. A soft pulse on the current step shows a worker that is busy right now, and the card counts the files changed, the questions raised about the work (answered and still open) and the docs and decision records the worker's session referenced, read or changed ("5 docs referenced · 2 changed"; it opens the task's Docs tab). While the automated review has questions for Firstmate, the checks line ("3 questions for Firstmate") and the question count open them in the card: each question in a sentence or two (the whole question opens in place), where in the change it is, whether it is still waiting on Firstmate, and once Firstmate answers, its call on that question (fix it, no change, keep as is) and why. It updates as Firstmate answers; the task page's **Timeline** shows the same questions where they were asked. An **Under way | Completed** toggle switches the cards between work still in progress (including what needs you) and landed or finished work, newest first (`?view=completed`); **Your move** shows only under Under way. A **Large | Compact | List** toggle sets the layout, remembered in this browser: **Large** is the full cards above; **Compact** keeps only the title, a project tag, the status, the passage strip and the question count; **List** puts one row per task with its project, current step, status, who it is waiting on (you, Firstmate, reviewers, the crew or earlier tasks) and when it last moved, and every column sorts. Each layout keeps the same sections.
- **Task page** (`/tasks/<id>`): the whole width, in two parts. A link to a place in it (say the Checks) opens there instead. For your own tasks its file opens in the reader. A stage starts where its history shows it was reached: Building when the worker started, Checks at the first validation run, Pull request when one is first named, Your review when it was reported ready, Landed at the merge. Each stage ends with what it produced: the files changed in a line (it opens **Changes**), the **Checks**, the pull request and its state, the report, a decision waiting on you, and plugin evidence. Stages not reached yet are listed last, as still to come. Every stage starts open; selecting one folds it to a line saying what it came to (say "4 files changed" or "Pull request #13 merged"), and **Fold all** and **Open all** do every one. The filters show **Everything**, only the **Conversation**, only the worker's **Updates**, or only **Checks and pull request**. On a wide screen the spare width beside it lists the stages, with when each was reached, to jump to. For work under way the timeline ends with **Now**, the worker's live console and the only place the page shows it (a bounded, read-only sample of its last lines, refreshed while it is on screen; select it to open it full screen), and **Jump to now** beside the tabs scrolls to it. **Checks** is every check in one place: the validation run's steps (rebase, review, tests, docs, lint, push, pull request, CI) with the same strip the cards show, each step with what it is doing or came to and how long it took (live for the step under way), and what each found opening in place, failures and the step under way open to begin with: for tests, how many passed and failed, each failed test with the start of its output and the scenarios the test step drove; for docs, which documentation changed and what the docs step wrote about it; the steps' own notes; the pull request's CI checks under the CI step; and the task's earlier validation runs. One that refuses to be framed says so, with **Open in new tab**. Under the page, **Open the review board** when the task's status lines name one, and plugins' buttons on the preview, such as Shared review's **Share for review**. Wherever else Wheelhouse links to a preview (the overview's preview line, the review evidence, a decision's evidence, the chat's preview cards), a stopped one says so instead of linking to an address that would not open. Beside it, **Talk it through** is a conversation about this preview with a helper (a headless Claude run, `claude -p`, given only this task: the page's text, the part you point at, the task's screenshots, which it may read, its instructions from Firstmate's backlog and its history; it keeps no session and loads no settings or MCP servers). **Point**, then a click on the page, says which part your next message is about: the element itself when the preview shares Wheelhouse's address, else the spot, which stays marked. The helper answers, asks back when it is unclear, quotes the instructions where they settle a question, and proposes each change you want as a line you can **Add to the list**. The list, **Your feedback**, is yours to edit, remove from or write into, and nothing goes anywhere until **Send to Firstmate**, which sends the whole list as one note about the task (`Re: <task-id>`) in Firstmate's inbox; Firstmate passes it to that same task's worker (it may add notes of its own, marked as its own), and the list shows in the Firstmate chat as your card addressed to Firstmate, with whether Firstmate has it and its reply. The conversation and list are kept in this browser, per task. `WHEELHOUSE_PREVIEW_CLAUDE` names the Claude binary the helper runs (default: `claude` on PATH) and `WHEELHOUSE_PREVIEW_MODEL` its model (default: sonnet). - **Documents** (`/files?path=`): a Markdown file Firstmate or a worker names, read in Wheelhouse. The document opens on the same paper sheet as a task's docs, read-only: raw HTML in it never runs (styles, forms, frames and scripts are dropped), and its links and images resolve against its own folder, opening other documents in the reader and images or text files from the same allowed folders.

An old `/tasks/<id>/review` address opens the same place, or the task's page when it has no pull request.

A second mate's question is marked **From second mate <id>** and names the task in its home; its answer goes to Firstmate about that second mate, to pass on, and a question about a task in its home cannot be closed from here, since the record of it is the second mate's (the second mate's own question, and work Firstmate holds on it for your call, are Firstmate's, as any worker's are). Each card says the question in plain words, Firstmate's recommendation when it recorded one, where the work can be seen, and what it rests on (**Evidence**: the review's findings, Firstmate's words, the pull request, the screenshots, and the report it names). **Where it is** is always on show when the task has one: **Open the preview** (full size here, with the preview helper while the task has a worker, and its address beside it to open in a new tab) and **Open the board** for a review board, both from the task's own latest status lines (see [What makes a preview show](#what-makes-a-preview-show)), never from the question's words; a preview or board that has stopped says so. A preview sign-off also shows the preview itself, live and scaled down. A second mate's question shows its task's preview the same way, reached through its forward for a remote one; for the second mate's own question, the preview its own status lines name, when a task in its home reported it. **Chat about this** (`Enter`) opens it in the Firstmate chat with the form that fits it and room to talk it through; **Agree** (`a`) sends Firstmate's recommendation in one tap; **Ask me later** (`l`) hides it in this browser for four hours; **Close** (`c`) takes a keyed question off without an answer; `j`/`k` move and `e` shows the evidence. A link to one card (`/inbox#card-<id>`, as the ship's bell's **Open decision** gives) opens it, even one snoozed or handled. Underneath, folded to a count, **Handled by Firstmate**: the questions Firstmate is settling itself (a worker's decision, a stuck worker, the automated review's questions), each with **Chat about this** to take it over, and the calls it made this week on your behalf (from **Decided for you**), each opening to its reason and the reviewer's own words, with **Change this call** (a message to Firstmate in the chat, not yet sent). Either way Wheelhouse does not try again until you ask again. Nothing on the page steers, messages or controls a second mate. Firstmate's scripts run with Wheelhouse's environment, with HOME, USER, LOGNAME, the usual PATH entries and, on macOS, launchd's ssh agent (SSH_AUTH_SOCK) filled in when the server started without them, so a remote second mate's reads find the SSH alias, keys and agent; and the snapshot's remote summary reads get 20 seconds together (`FM_SNAPSHOT_BUDGET`, unless set) rather than Firstmate's default 5.

### The Firstmate session

`wheelhouse open` starts the one Firstmate session when none is running: an ordinary interactive `claude` in Firstmate's checkout, inside a detached tmux session named `wh-firstmate` on Wheelhouse's own tmux server (`tmux -L wheelhouse`; change the name with `--tmux-socket <name>` or `WHEELHOUSE_TMUX_SOCKET`), never the default server the crew run on. It is the same session you would start in a terminal, so Firstmate's own hooks and supervision run unchanged.

- **One session only.** Firstmate's session lock decides: when `fm-inbox.sh ready` says another session holds it (say, Firstmate running in your own terminal), Wheelhouse starts nothing and shows that session's conversation read-only, since it cannot type into a terminal it does not own; the message box then sends to Firstmate's inbox (`fm-inbox.sh note`, see [Messages and retries](architecture.md#messages-and-retries)), and Firstmate's reply appears in the conversation. If the lock cannot be read, it starts nothing either. If starting fails, **Start Firstmate here** on the home page tries again, under the same rule.
- **It outlives Wheelhouse.** The session belongs to tmux, so closing the browser or Wheelhouse leaves it running, and the next `wheelhouse open` shows it again. To use your own terminal, run `tmux -L wheelhouse attach -t wh-firstmate`.
- **Permissions.** It starts with `--dangerously-skip-permissions` (and Claude Code's bypass-mode confirmation skipped), so Firstmate runs without stopping to ask; `--no-skip-permissions` starts it without, and Claude Code's permission prompts then appear in the terminal drawer. Before starting it, Wheelhouse pre-approves Claude Code's workspace trust for Firstmate's checkout (`hasTrustDialogAccepted` in `${CLAUDE_CONFIG_DIR:-$HOME}/.claude.json`, written atomically; no other setting is touched). `FM_HOME` is passed when the home differs from the checkout.
- **Its transcript.** Wheelhouse adds one SessionStart hook of its own through `claude --settings` (merged with Firstmate's hooks, never replacing them), which writes the hook's input, including `transcript_path`, to `<state-dir>/firstmate/session-start.json`. The chat follows that file, and finds the new one after `/clear`, `/compact` or a restart. For a session it did not start, it looks up the Claude session id Firstmate records beside its lock (`state/.lock-session`), else the newest transcript whose records name Firstmate's checkout. It only ever reads the transcript, and reads at most its last 8 MiB when first opening it (earlier messages stay in the terminal).

The chat shows the captain's messages (including ones typed while Firstmate was busy), Firstmate's replies as Markdown (a long, structured reply, 500 characters or more with a list or heading, such as a plan or a round-up, as a **Briefing** card under a gold rule, headed with the conversation's title), and its work between replies folded into one line ("3 commands, 1 skill"; "Thought for 7s") that opens to a row per step and then to the step's input and result. Claude Code records only a sealed signature for its thinking, so thinking shows as how long it took, not the words. A turn started by a background wake (a task notification) whose reply is empty or only an all-clear such as "Captain, shipshape." is kept out of the chat; the **ship health** pill in the chat's bar (All well, N need you, Keeping an eye on a problem, Something failed) says when the last background check ran, or that one is running, and lists recent ones. A wake with something to say reads as an ordinary message. Slash commands and their output show as they do in the terminal.

- **Typing.** Enter sends, Shift+Enter adds a line. A message shows in the chat at once, faded, with where it is: **Sending…**, **Queued** (Firstmate was busy, so Claude Code holds it until the turn ends), **Delivered** (waiting for it to appear in the session), or **In Firstmate's inbox**; it becomes an ordinary message when the session's transcript records it, in whatever form Claude Code hands it over (a large paste wrapped in its paste tags, several queued messages delivered as one, or a mid-turn reminder). A mid-turn reminder shows as your message at the point Firstmate read it. One the transcript never shows recognisably is let go once Firstmate has finished two turns since, rather than staying faded below them. If it could not be sent, it says why and offers **Retry** and **Discard**. The message is pasted into the session as one bracketed paste (`tmux load-buffer` and `paste-buffer -p`), then Enter, so a multi-line message never submits early. `/` at the start offers Firstmate's commands (its skills marked `user-invocable: true` and its `.claude/commands`) and the Claude Code built-ins that work from a chat (`/compact`, `/clear`, `/context`); built-ins that open a picker in the terminal are left out. Typed anyway (`/mcp`, `/model`, `/config` and the like), such a menu shows in the chat as a card: numbered choices as buttons, and otherwise **Close menu**, which presses Escape only while the menu is on screen (as often as its nested screens need), and **Use it in the terminal**. While any menu or question is open, nothing is typed into the session, where Enter would choose in the menu: your message waits in the box until it closes. `#` anywhere offers tasks and pull requests (and the chat's threads, see **Threads**) and inserts a chip, which Firstmate receives as `[task <id>: <title>]` (or `[PR <url> — task <id>: <title>]`), the task id being the key its own scripts use. While Firstmate works, an empty message box offers **Stop**, which presses Escape in the session.
- **Replying.** To answer a particular message, yours or Firstmate's, as in WhatsApp: hover over it and click the reply arrow beside it (or tab to it), or on a phone swipe the message to the right, or hold it to show the arrow. The start of that message shows above the message box, with a cross (or Esc) to cancel. The sent message carries the quote at its top; click the quote to scroll back to the original, which lights up for a moment. Firstmate only receives text, so the quote reaches it as one Markdown line before your words: `> Replying to Firstmate: “<the first 140 or so characters, as plain text>”`, a blank line, then your message (`Replying to my message` for one of yours). The chat recognises that form when it comes back in the transcript and shows it as a reply. A slash command typed while replying is sent as the command alone, without the quote, so it runs. A quote whose message is no longer in the chat (it shows only the most recent part of a long conversation) still shows, but leads nowhere. A message of attached files alone has no words to quote, so it offers no reply. There is no reply while Firstmate cannot be messaged.
- **Thumbs-up.** Beside the reply arrow on Firstmate's messages (shown on hover, by tabbing to it, or by holding the message on a phone) is a thumbs-up button. One click marks the message with a small 👍 and sends Firstmate a short note quoting its first line as plain text, `👍 on: “<up to 100 or so characters>”`, as an ordinary chat message, so Firstmate knows it was liked or acknowledged. Clicking again takes the 👍 back and sends nothing. The mark is kept by Wheelhouse with the message (in its state directory, `chat-reactions.json` beside the message store, the most recent 1000), so it stays after a reload and shows on every device, a phone included; an open page reads the marks again when it regains focus. Firstmate is told only when the server newly keeps the 👍: a message already marked from another device, or a mark Wheelhouse cannot keep, sends nothing. There is no thumbs-up while Firstmate cannot be messaged, though marks already given still show.
- **Attaching files.** The paperclip at the left of the message box attaches files; so does dropping files anywhere on the chat, or pasting an image or file into the box when the clipboard holds no text (pasted text is typed as before, even when the clipboard also holds a picture of it). A pasted image with no name of its own (a screenshot, say) gets one like `Pasted image 2026-10-31 09.05.07.png`. Each file uploads at once and is listed under your text with its kind and size (an image with a small thumbnail), how far it has got, or why it failed; the cross removes it, stopping an upload still under way. Send waits until uploads finish, and a message can be files alone. A file may be up to 25 MB; a larger one says so and is not uploaded. Firstmate receives your words followed by one line per file, `[attached file <absolute path> — <name>, <size>, <type>]`, and opens the file with its own tools (with `--no-skip-permissions`, reading a file outside its checkout may ask first, in the terminal drawer). In the chat the message shows a **N files attached** card listing each file, with a thumbnail for a PNG, JPEG, GIF, WebP or AVIF image (click to enlarge), and keeps it once the transcript records the message. This works the same when messages go to Firstmate's inbox.

  Files are kept on this machine in Wheelhouse's state directory, `<state-dir>/uploads/<day (UTC)>/<random id>/<name>` (by default `~/.local/state/wheelhouse/uploads/`), never in Firstmate's home, a project clone or a git repository, readable only by your user. Names are cleaned (no folders, control characters or characters shells treat specially; at most 120 characters, extension kept). Wheelhouse deletes each day's folder seven days later, when it starts and whenever a file is attached; a message older than that still lists its files, without thumbnails. Uploads use the same guard as every change (loopback `Host`, the page's own `Origin` and this launch's session token). Wheelhouse never runs an uploaded file or renders it as a page: thumbnails are served only for files whose bytes are one of those image formats, with that type, `X-Content-Type-Options: nosniff` and a sandboxing `Content-Security-Policy`; anything else, SVG and HTML included, is listed by name only.

- **Dictating.** The microphone beside Send (also under a preview) dictates into the box: click it, or press Ctrl/⌘+Shift+Space in the box; held down, the shortcut listens until you let go. Words appear as you speak, the part still being recognised in a lighter colour, and stay as ordinary text to edit; nothing is ever sent for you. Click again to stop, Esc to cancel and put the box back, or just start typing. Dictation uses the browser's Web Speech API, which Chrome and Edge provide by sending the audio to their speech service (Google, in Chrome); Wheelhouse says so once before first use. In a browser without it, or with the microphone blocked, the mic says so plainly. The engine sits behind a small interface (`src/lib/voice/engine.ts`) so a private local engine can be added later.
- **Questions.** When Firstmate asks with Claude Code's question picker, the chat shows the question with its options as buttons; picking sends the keys the picker expects, worked out on the server from the open question. Free-text answers go through the terminal.
- **Live previews.** Every preview Firstmate links shows as a live box under the reply that links it: the page scaled down from desktop size, and **Full size** and **New tab**. A preview a task reported is that task's card, with its project, its pull request and checks, and **Open the board** when it also reported a review board; any other address on this computer a reply links (a preview Firstmate serves itself, a port it forwarded from a second mate, a Lavish board) is a box of its own, with its address in place of the task. In the box the page is a picture (it takes no clicks); clicking it, or **Full size**, opens it full screen, growing out of the box, with the preview helper when it is a task's, as on the task page. On a phone, full screen is the page alone under a bar with Close, its title and address, and Reload; a dock at the foot switches it between the phone's width and a desktop's (scaled to fit), opens it in a new tab, opens the helper as a sheet over the page (it steps aside while you point), and holds **Share for review**. While the preview does not answer, the box says **Preview stopped** in one quiet line, with no **Full size** or **New tab**, and shows the page again once it answers. Each task has one card, under the latest reply since it reported its preview that links that preview (else the first reply about it); once the work has landed, it moves under the first reply about it since and says **Landed**. Each other address has one box, under the latest reply that links it. A plugin can add a button to every box: with [Shared review](../plugins/shared-review/README.md) on, **Share for review** starts a shared review of the live app in one click (see [What makes a preview show](#what-makes-a-preview-show) for exactly what makes a box appear). The preview is embedded only after Wheelhouse has checked it is on this machine and answering, under the same rules and sandbox as the task page's.
- **Decisions.** Every question Firstmate escalated to you shows in the chat as a card of its own, at the time it was asked, whether or not Firstmate mentions it: what is being decided, Firstmate's recommendation and the evidence, answered with the form that fits it rather than the same three buttons. Two plain answers are one tap each (**Merge** / **Not yet** on a merge call, **Go ahead** / **Not like this** on work held for you, **Sign it off** / **Request changes** on a preview); options the question names are picked, then sent with **Decide**; several calls keep their own choices; and a held question that asks which, what or how takes a written answer. **Add a note** goes with any of them. A question Firstmate is settling itself shows only once you bring it in (**Chat about this** on the Decisions page, `/?decision=<card id>`, which also opens its discussion) or have talked about it. The answer goes to Firstmate as a message, and the question leaves Decisions and On deck at once; it stays where it was in the chat, folded to **You decided …**, your note and whether Firstmate has it, however you answered it. **Discuss** opens a thread under the card for talking it through with Firstmate before (or after) you answer, with a few starting questions such as "What are the other options?"; asking answers nothing. Each question goes to Firstmate as an ordinary chat message that starts with a quote naming the task and decision (`> About the decision on <task> (key <key>), not an answer yet: “<the question>”`) and a second quoted line telling Firstmate how to change the form: when its reply ends with a `decision-form` block (the question on its first line, then `- option` lines, `- label: what it means`, `(recommended)` on one, or `- (written)` for a written answer), that becomes the form you answer with, marked as changed after your question, and what you decide from it goes to Firstmate in its own words. Only a reply about the question as it is now asked changes the form: when Firstmate asks again under the same decision with a new question, the talk about the earlier one folds away under **Earlier question: “…”**. The chat shows the question, with the reply Firstmate starts right after it, in the thread rather than in the conversation. While Firstmate runs in another terminal (the chat is read-only), the question goes to Firstmate's inbox instead, and its answer shows in the conversation, as any inbox message's does. Wheelhouse keeps a record of the answers it sent (`<state-dir>/homes/<home>/answered-decisions.json`, the last 300) so a question keeps its folded card after Firstmate settles it; once such a question has left Decisions, its answer is left out if it is older than the conversation shown, while a question still in Decisions, open or answered, shows first. A feedback list sent from a task's preview, or from a plugin that may send them (see [Sending feedback to Firstmate](plugins.md#sending-feedback-to-firstmate)), shows here too, as your card addressed to Firstmate, at the time it was sent.
- **Secrets.** The key button beside the paperclip opens **Add a secret**: a name, a value in a hidden field and, optionally, the projects that may use it. The value goes straight to the vault (the macOS login Keychain, through `wh-vault`), never into the message box, the chat or the transcript; the field is emptied once Wheelhouse answers or the popup closes. For a name the vault already has, the popup asks whether to replace it, and **Replace** has you type the value again; on a computer without the macOS Keychain the popup says it cannot store one. Once stored, the chat sends Firstmate `Stored secret <name> in the vault.` and which projects can use it. Firstmate can ask for a secret with a `vault-request` block in a reply (the name, and optionally why and the projects); the chat shows it as a card under the reply whose **Add <name>…** opens the popup filled in, and the card shows **Stored in the vault** once you store it. Nothing opens until you click. See [The vault](vault.md#from-the-chat).
- **Questions as forms.** Firstmate can also ask you something in the conversation itself, outside any decision card, by ending a reply with the same `decision-form` block. The chat shows the reply's words without the block, then the form under them: two short options as one tap each, more picked and then sent with **Decide**, or a box for a written answer, with **Add a note** on any of them. Answering sends your pick to Firstmate as your own chat message naming the question it answers (`Decided: <the option's words> — for: “<the question>”`, or `Decided: <the option's words>` for a form without a question line, with your note after a blank line), and the form then shows **You decided …** with nothing left to press. Each form waiting for an answer can be answered on its own while it is the latest form asking its question, so an answer sent while Firstmate went on to ask something else still answers the form it was for; a form without a question line can be answered only while it is the latest form. A form a later one asking the same question (or, without a question line, any later form) replaced stays closed. An older `Decided: …` message that names no question answers the latest form only when its words are one of that form's options (any words for a written answer). Whether a form is answered comes only from the conversation's own records: the transcript for an answer typed into the session, and Wheelhouse's record of the notes it sent to Firstmate's inbox (by when each was sent, leaving out one whose delivery failed) for an answer sent there while Firstmate runs in another terminal, so the form stays answered after Firstmate's next turn and after a reload. Your answer message counts once, for one form asked before it (the latest asking, when the same question was asked again), from when it is being sent; an answer that fails to send and is discarded, or an inbox note whose delivery fails, leaves the form open again. A block with more words after it (an example, say) stays as text.
- **Threads.** Every message, decision card, preview card and feedback list carries a small tag naming its thread: a project, or a free-standing topic such as "Time capsule". Firstmate files a reply under a thread with an invisible marker line, `<!-- project: <slug> -->`, at the start of the reply or of each section of a round-up about several; a section runs until the next marker, and the slug is a registered project's id or name, else a topic of its own. A round-up shows each section with its own tag, its words before the first marker as its introduction. Cards take their task's or decision's project. Without a marker, the tag is a guess, and says so: the one project of the tasks a message names (its id, pull request or preview address), else, for Firstmate's answer to you, the thread of your message; anything else is **Unsorted**. Click a tag to move the message to another thread or a new topic; the move is kept in this browser. The header's project switcher picks the thread to read on the home page: projects, with how many messages each has in the chat (picking one scopes On deck too, as before), and under **Chat topics** the topics and Unsorted (`/?thread=<topic>`). Reading one thread shows only its messages, with a note saying how many of the chat's that is and **Show all threads**; a round-up shows only its sections about the thread, with how many parts are about others, except one that ends in a form, which shows whole so the form can be answered there. **Fold other threads to a line** instead keeps the timeline, each run of other threads' messages one line that opens in place, dimmed. Messages you send while reading a thread are sent in it: the box says **Sent in** the thread (the cross sends this one in none), and Firstmate receives `[project <slug>] ` before your words (after a reply's quote). `#` also offers the threads, and picking one, or starting the message with `#<thread>`, sends that message there instead. Slash commands are sent as they are.
- **The terminal drawer** shows the session's own screen, live, for anything the chat cannot show. Its full-screen button puts it in the browser's full screen (filling the window where the browser refuses), keeping the same connection; the terminal refits to the new size and the session's tmux window follows. Esc still goes to the session where the browser allows it (hold Esc to leave full screen; elsewhere Esc leaves it), and the button beside it restores the drawer. It is a WebSocket at `/api/firstmate/terminal`, served on `127.0.0.1` only, backed by a real pty (`node-pty`) running `tmux -L <socket> attach-session -t =wh-firstmate`.

Everything that types into the session (sending, Stop, answering, closing a menu, the terminal) is refused unless its `Host` is loopback, its `Origin` is the page's own and it carries this launch's session token (as a WebSocket subprotocol for the terminal), and it reaches only `wh-firstmate` on Wheelhouse's own tmux server, and only when Wheelhouse runs it.

### What makes a preview show

Wheelhouse finds previews in two places, and Firstmate can rely on both:

- **A worker's status line** records the task's preview: `preview <url>` (the convention, any address), or an address on this computer (`http://127.0.0.1:<port>/…` or `http://localhost:<port>/…`) right after the word "preview" (`direct preview http://…`, `the preview at http://…`), or the first such address in a line that announces a preview ("Preview ready", "preview:", "preview is up", "prototype … ready"), such as `needs-decision [key=board-review]: Preview ready for approval: … - http://127.0.0.1:4471/`. The same line can name a **review board**: an address on this computer whose path is a board session (`/session/<id>`, as a Lavish board's is), or one right after the word "board" (`on Lavish board http://127.0.0.1:4387/session/c03d…`); the preview is then the line's other address, the one after the word "preview" when there are several (`(direct preview http://127.0.0.1:4612/)`). An address in any other line (`tests hit http://localhost:9222/json`, `fixed redirect to http://localhost:3000/callback`, `preview tests pass against http://localhost:9222/json`) or inside code is neither. The latest line that names one wins. That is what the task page's **Live preview**, the chat's task card and the decision cards' **Where it is** show. A second mate's task's lines are read the same way, in its own home.
- **A Firstmate reply** shows a box for every address on this computer it links, in plain text, bold or a Markdown link, except inside code (`` `http://localhost:3000/callback` `` and fenced blocks are not previews) and Wheelhouse's own pages. One box per server under a reply (`/a`, `/b` and `/c` of one prototype are one box), at most three. The page a task still under way reported is that task's card instead, and a reply links a task only by that exact page; a reply that shows a task's card (landed or not) shows no other box for that card's page, and it takes over from earlier replies' boxes for it; for a second mate's task, the reply may name the task by its id in its own home (`wh-style`, for `wh-style@far-mate`).

So, to be sure a preview shows: the worker reports it in a status line, and Firstmate's reply about it includes its address on this computer outside code. A remote second mate's preview is the task's address as the worker reported it (Wheelhouse forwards it); a port Firstmate forwarded itself (`ssh -L`) shows as a box of its own.

### The ship's bell

The bell rings for the moments that matter, on whatever page you are on: **PR green** (a pull request passed its checks and waits on your merge), **Question waiting** (Firstmate is holding a decision for you, or is asking you something in its session: its question picker or a permission prompt), **Worker stuck** (a worker reported itself blocked or failed, Wheelhouse lost contact with it, or a working task has had no word for 20 minutes with nothing running), **Merge landed** and **New issue** (a GitHub issue you watch, for projects whose GitHub issues setting is **Ring the ship’s bell** (`bell`); see [Plugins](plugins.md#github-issues)). Each shows as a toast at the top right, under the header and clear of the chat's message box, newest first, with one-tap actions: **Merge** (on a green PR), **Open decision** (the decision itself, open in its card on the Decisions page, even one you asked about later; for a second mate's task, its task page), **Answer in chat**, **Open task**, **Ask Firstmate**, **Open PR** and, on a new issue, **Hand to Firstmate** (a note with the issue's URL, repository and title, sent once). **Merge** never merges anything itself: it sends Firstmate a note asking it to merge that pull request, through `fm-inbox.sh note` like any other message, and says **Asked Firstmate to merge** once Firstmate has it; a second tap, or a tap in another tab, sends nothing more. Three toasts show at once; the rest fold into **+N more**. News closes itself after a few seconds (not while the pointer is on it); a toast that waits on you stays until you dismiss it or its moment passes (the PR merged, the question answered, here or in the terminal).

Wheelhouse raises each alert once while its moment lasts (a moment that passes and comes back, such as a PR that goes green again after rework, rings again), on the server, from the same records it already reads, and only for moments that happen while it is running: what is already true when it starts is on the board, not news. Your browser remembers what it has rung, so an alert rings once however many Wheelhouse tabs are open and however often you reload; a toast you dismissed stays dismissed in every tab. The tabs share one connection to Wheelhouse (one tab holds it and passes events to the others, and another takes over when that tab closes), so many open tabs never use up the browser's connections.

The bell in the header lists the recent alerts and holds this browser's settings: which kinds ring, **Bell sound** (two strokes of a ship's bell, off until you turn it on; **Ring the bell to hear it** plays it), and **Browser notifications** (off until you turn them on, which asks the browser's permission). A notification shows only when no Wheelhouse tab is in front, and selecting it opens the task, never a merge. The tab you are looking at plays the sound; with none in front, the tab holding the connection does. Toasts come and go without moving when your system asks for reduced motion.

### The messaging gateway

The gateway lets you reach Firstmate from your phone, through a Discord bot of your own. It is part of Wheelhouse itself, not a plugin, and Discord is its only channel for now.

- **Messages to Firstmate.** A direct message you send the bot goes to Firstmate through `fm-inbox.sh note`, exactly like a message sent from the browser, with a first line (`[via Discord] …`) saying it came from your phone and asking Firstmate to answer with `fm-inbox.sh reply`. Its request id is the Discord message's own id (`discord:<id>`), so a message Discord delivers twice is still one note. Reply to one of the bot's alerts or decisions (or to one of Firstmate's answers) and your message is about that task (`Re: <task>`). The bot marks your message 📥 once Firstmate has it and 👀 once Firstmate has read it, and Firstmate's reply comes back under it. Only text is passed on: attachments, stickers and forwards are not, and the bot says so. `status` (the crew at a glance, from what Wheelhouse already reads) and `help` are answered by Wheelhouse itself and wake nobody. At most 6 messages a minute and 200 a day are passed on, since each one wakes Firstmate.
- **Alerts and decisions.** The [ship's bell](#the-ships-bell)'s alerts of the kinds you pick (**Question waiting**, **PR green** and **Worker stuck** to begin with) arrive as messages. **Merge** on a green PR is a button that sends the very note the browser's **Merge** sends, with the same request id, so a tap on the phone and a click in the browser ask Firstmate once. A question with a card in **Decisions** arrives as that card, its **Approve**, **Fix** and **Skip** as buttons. A question whose text names options never sends picks you did not see: a single call's options are buttons of their own (each sends that pick) when they fit beside **Fix**, **Skip** and any **Open PR** link; otherwise, and always with **Titles only** on, the picks are made in Wheelhouse, through an **Open in Wheelhouse** link. Once the card is answered, here or in the browser, or closed, a button sends nothing more and says why. Pull request links open on the phone; Wheelhouse's own pages are on your Mac's loopback, so **Open in Wheelhouse** opens only on that Mac, and alerts leave them out. A button holds only a random token for an action Wheelhouse keeps: it works once, for 24 hours, and only for you.
- **Never from a chat.** Nothing you send the bot types into the Firstmate session, answers its question picker or its permission prompts, or reaches a worker. A question Firstmate asks in its session arrives as a notice to answer it at the keyboard.
- **Who is heard.** Only the account you pair. Anyone else who messages the bot gets no answer at all, and messages in server channels are ignored, yours included. Pairing binds your Discord user id, which never changes, not your name.
- **The bot token** is set only with `wheelhouse gateway connect discord`, which asks for it with the input hidden (or reads it from stdin), never from the command line, where other processes could see it. It is kept in the macOS Keychain (a password item for the service `wheelhouse-gateway`, account `discord:<digest of the gateway directory>`, so each config directory has its own token and a Wheelhouse started with another `--config-dir` starts with none), written through `security`'s standard input so it never appears on a command line either. Where the Keychain cannot be used, it is kept alone in `<config-dir>/gateway/discord.token` (see `--config-dir`) instead, readable by your user only. Either way it is never in the Firstmate home, a project or a worktree, never in the environment of anything Wheelhouse starts, and never in a log. A config directory inside the Firstmate home keeps the gateway off. The gateway's other settings (on or off, the paired account, the alerts, titles only) are in `<config-dir>/gateway/settings.json`.
- **What leaves your Mac.** Alerts (the task's title and one line about what happened), decision questions, Firstmate's replies and the `status` summary go to Discord, which does not encrypt bot chats end to end. No diffs, terminal output or screenshots are sent. With **Titles only** on, alerts and decisions say only what kind of alert it is and which task (a decision, only its task): no alert text, question or recommendation. Their buttons and pull request links stay.
- **Only while Wheelhouse runs.** The gateway runs inside Wheelhouse's server and only connects out to Discord (one WebSocket, and HTTPS calls); it opens no port, so Wheelhouse still listens on `127.0.0.1` only. For use away from the keyboard, leave Wheelhouse running, for example `wheelhouse open --no-browser` in tmux, and keep the Mac awake. Run one Wheelhouse per bot: two would both answer the same messages.
- **Its record.** Which phone messages it passed on and the buttons it handed out are kept in `gateway.json` beside the home's messages in the state directory; every message accepted or refused (with why), every send and every press is logged in `<state-dir>/gateway/discord.jsonl`.

#### Setting up Discord

You need a Discord account, with two-factor authentication on (whoever holds the account can message Firstmate), and a server of your own for the bot to share with you: a bot can only exchange direct messages with people it shares a server with.

1. Open the [Discord Developer Portal](https://discord.com/developers/applications), choose **New Application**, name it (say, Wheelhouse) and create it.
2. On **Installation**, set **Install Link** to **None**: Discord will not make a bot private while it has one.
3. On **Bot**, turn **Public Bot** off, so that only you can add it to a server. Leave **Presence Intent**, **Server Members Intent** and **Message Content Intent** off: Wheelhouse asks only for direct messages, which need none of them. Choose **Reset Token** and copy the token (Discord shows it once).
4. In a terminal on the Mac that runs Wheelhouse, run `wheelhouse gateway connect discord` and paste the token at the prompt. Wheelhouse checks it with Discord, warns if the bot is still public, saves it, and prints a link that adds the bot to a server.
5. If you have no server of your own, create one in Discord (**+**, then **Create My Own**). Open the link from step 4 and add the bot to that server; it needs no permissions. Keep **Direct Messages** on in the server's **Privacy Settings**.
6. In Wheelhouse, open **Settings** (the gear in the header). Within a few seconds Discord shows **Connected** as your bot. Choose **Pair an account**: a code shows for ten minutes.
7. In Discord, open a direct message with the bot (its name in the server's member list, then **Message**) and send the code. The bot answers that you are paired, and Settings shows your account.

Tick which alerts arrive, and whether they come as titles only, in Settings → Gateway. To stop, use **Turn off** there or the commands below. If the token may have leaked, choose **Reset Token** in the Developer Portal (the old token stops working at once) and run `wheelhouse gateway connect discord` with the new one.

| Command                                  | Does                                                                                                                              |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `wheelhouse gateway connect discord`     | Set the bot token (asked for, hidden), after checking it with Discord; it replaces the one before                                 |
| `wheelhouse gateway off` / `on`          | Turn Discord off (it neither reads nor sends) or on again                                                                         |
| `wheelhouse gateway unbind`              | Forget the bound account; no one is heard until you pair again                                                                    |
| `wheelhouse gateway titles-only on\|off` | Send alerts and decisions as titles only, or in full again                                                                        |
| `wheelhouse gateway status`              | Where the token is kept, on or off, who is bound, the alerts, titles only, and the running Wheelhouse's connection (`--port <n>`) |

Each takes `--config-dir <dir>`, and a running Wheelhouse picks up the change within a few seconds.

### Passage steps

| Work  | Steps                                                            |
| ----- | ---------------------------------------------------------------- |
| Ship  | Queued → Building → Checks → Pull request → Your review → Landed |
| Scout | Queued → Scout → Report → Your call → Done                       |

The steps follow Firstmate's delivery mode: direct-PR work has no local Checks step, local-only work has no Pull request step, and with yolo on there is no Your review step because Firstmate merges the work itself. In no-mistakes mode the pipeline opens the pull request before CI runs, so CI checks appear under Pull request. Its CI monitor keeps running until the pull request merges, so an open, non-draft pull request whose checks are green moves to Your review (and **Needs your review**) even while that monitor is still working. Whose review it is comes from GitHub, not a guess: when its review is requested of other people, or the base branch requires an approval and you opened the pull request yourself (GitHub never counts the author's own approval), it is **Waiting on reviewers** instead ("Pull request #12 is waiting on approval from @alice"), with the reviewers named, and it does not count as needing you. A review requested of you is yours, and once GitHub says it is approved it is yours to merge ("approved and ready for you to merge"). Once you ask for changes after it was reported ready, it is the worker's turn and the task starts a new **run**. A change sent from Wheelhouse goes, through Firstmate, to the worker that opened the pull request while that worker is still live, so no second session starts; only when that worker is gone does Firstmate start a new one for the run (see [Messages and retries](architecture.md#messages-and-retries)). Runs are counted the same way either way: run 1 is the first build up to its ready report, and run 2 (then 3, and so on) goes back to the start of the build cycle, Building, then Checks once its validation run starts, then Pull request once it pushes or its CI runs, and Your review when the worker reports the pull request ready again. Cards, On deck, the radar (whose dot moves back to Building) and the task page name the run with its step ("Run 2 · Building"), and the merge call leaves the Decisions inbox until the run is ready. Asking for changes is any of: a review comment on a file or line, a changes-requested review or a commented review that says something, or a comment on the pull request on GitHub that is more than approval or merge chatter (a comment that is only "LGTM", "looks good", "approved", "ship it", "merging after lunch" or emoji does not count; one that adds anything, such as "LGTM once the docs are updated" or a question, does); new commits pushed to it; feedback typed under the live preview, or **Fix** / **Request changes** in the Decisions inbox; or a `working:` status line from the worker after the ready report. A plain chat message does not start a run, since it may only be a question; use one of those actions to ask for changes. Wheelhouse keeps the change requests it sent (the latest 2000) apart from the other messages in its message record, so a task's runs do not depend on how many other messages have been sent since. The worker's next ready report ends the run and hands the pull request back to you, whether or not it pushed new commits (it may have only answered a question). Feedback from bots never counts, and neither do replies inside a review thread; the pull request author's own comments count only when the author is the account Wheelhouse reads GitHub as (you reviewing a pull request opened under your account), since otherwise the author is the worker. On the task page, the **Timeline** marks where each later run started, with the changes that started it as a checklist (each request with where it came from, its file and line and a link to it on GitHub, ticked once its thread is resolved on GitHub or the worker has reported the pull request ready since), so each run's work, validation runs and screenshots follow it in time order. A card counts the current run's changes ("Run 2: 2 changes to make · 1 done"). These built-in passages are written in the passage file format (`src/lib/server/passages/builtin.ts`), and a project can add steps such as Deployed or Released to them with a [passage file](passages.md).

### Second mates

A second mate itself is never a task card: its own record in Firstmate's fleet (a task of kind `secondmate`) shows on the Second mates page, as a crew of its own on On deck (its heading and toggle segment) and in the Harbour's Second mates list. Its home's work, though, sits beside your own crew's, the same way:

- **In the same lists and cards.** Each task in a second mate's home is a task like any other, named `<task>@<second mate>` (no task of yours can be, since a task id has no `@`). It sits in Under way, Up next, Needs you, Landed (on On deck, under its second mate's heading), the Harbour's charts and its project's page. Its card carries two tags side by side: a badge with the second mate's name (for a remote one, its host as secondary detail), then its project tag, drawn as on your own cards. Its status comes from Firstmate's summary of that home, and its project from that summary or else the task's `state/<task>.meta` there, as for your own tasks. Its pull request and preview come from its status log there, read in the background a couple at a time and at most once a minute while it is in flight: a local second mate's file directly, a remote one's with `fm-on.sh <mate> fm-remote-file.sh get state/<task>.status`, read-only. Like your own tasks, it leaves Under way once GitHub says its pull request merged (Landed) or closed without merging (Closed). Only the last 256 KiB of its status log is read; a remote one past 1 MiB, the most `fm-remote-file.sh` sends, takes its pull request from the `pr=` its meta file records, keeps the preview last read (or says the history was cut), and its history says it is cut.
- **The same task page.** Open it and you get the task page your own tasks have: status, history (its status log), pull request, the live console (`fm-peek.sh` in that second mate's home, over `fm-on.sh` for a remote one, looked at no more often than every 5 seconds however many cards ask), its instructions (its brief in that second mate's home, read-only, first on the Timeline), its **files changed** (under **Changes**, each opening its diff, and counted on its card), and the **Live preview** with the preview helper. The files come from the task's worktree, read as your own tasks' are: `git diff` against the merge base with its base branch, uncommitted and untracked files included. For a second mate on this computer that is its worktree here; for a remote one, the worktree its task's meta records on its host, read with read-only git over the second mate's own SSH alias (the one Firstmate's `fm-on.sh` uses), with nothing fetched. The list is read at most every 30 seconds however many pages ask, and in the background about once a minute for its card; a file's diff is read only when you open it. When the host cannot be reached the task page says it is offline, and the card keeps the count it last read.
- **Previews from another host.** A remote worker reports its preview on its own host's loopback, which your browser cannot reach. Wheelhouse listens on a port of its own on 127.0.0.1 and carries each connection to the reported port over the second mate's SSH alias with `ssh -W 127.0.0.1:<port> <alias>`. That carries that one port and nothing else: no forward from your SSH configuration, no agent, no X11, and no port opened on the host. It opens only when a preview is asked for and closes once nothing has asked for five minutes, when the task leaves the second mate's work in flight, or when Wheelhouse stops. A host ssh cannot reach reads as offline.
- **Preview comments and feedback go to its second mate.** A preview list, or any note sent about the task, goes as one note in that second mate's own inbox (`fm-inbox.sh note`, over `fm-on.sh --stdin` for a remote one), `Re: <task>` under the id its home knows. It never goes to your Firstmate, and never to a task of yours with the same id. A host that cannot be reached is not sent to again by itself.
- **Chat about it with Firstmate.** **Chat about this**, or `#` in the message box, names it to Firstmate as `[task <task> on second mate <mate>: <title>]`, so Firstmate passes your words on, and its replies come back in the chat as any do.
- **Its questions** are cards in Decisions, as above, and a hold of its waits in Your move.
- **Its projects** are in the project list beside yours. A project with a second mate's work says so on its Harbour card (**Work on second mate &lt;id&gt;**), and its page lists that work with your own.

### Honest gaps

Wheelhouse shows what Firstmate records and says plainly what it cannot see:

- **Deployments** are not recorded by Firstmate. A Deployed (or Released) step, and the watch report's "N live", appear only for projects whose [passage file](passages.md) declares one and the checks that observe it.
- **Preview links** appear only where a worker's status line or a Firstmate reply names an address on this computer (or a `preview <url>` line names one elsewhere); see [What makes a preview show](#what-makes-a-preview-show).
- **Second mates' host load.** Firstmate's fleet snapshot does not report a second mate's host CPU, memory or disk, so the Second mates page says it is not available. Firstmate's summary of a second mate's home also carries no preview address or pull request for work in flight. Wheelhouse reads those from each task's status log there instead, so they appear up to a minute after the worker reports them.
- **Decisions** Firstmate holds for you are recorded as text, without structured options. Wheelhouse reads the options from that text where it can: lettered options (A, B, C), numbered calls each with their own options ("1) Approach: A … or C …", "(1) … yes / no", "Q1: …"), the one marked (recommended) or (rec), which starts picked, and a closing question, which becomes an optional yes/no; a call that cannot be split cleanly takes a written answer, and a report the question names (a Markdown file in Firstmate's `data/` folder) opens in the card with **Read the report**. Picks go to Firstmate as one line ("1) Approach: A (core gateway) 2) First channel: Telegram") with your note. Text with no options it can read gets the two plain answers that fit the kind of question, or a written answer. What Firstmate escalated is what it holds for you (a captain hold), a green pull request waiting for the word to merge, and a preview waiting for sign-off; every other open question (a worker's decision, a stuck worker, the automated review's questions) is Firstmate's to settle, so it sits under **Handled by Firstmate**. **Close** (or `c`) takes a question that no longer needs you off the stack without an answer, as long as Firstmate records it under a decision key: Wheelhouse asks Firstmate to record it resolved on its key, and the card leaves at once (it comes back only if the question is raised again). A captain hold or a merge call closes by being answered. Questions Firstmate asks with Claude Code's question picker show as buttons.
- **The messaging gateway** works only while Wheelhouse runs, and only through Discord for now.
- **Firstmate's thinking** is not shown as words: Claude Code keeps only a sealed signature for it.
- **Inbox messages** (sent when Firstmate runs in another terminal) report delivery and acknowledgement as a yes/no: Firstmate does not record when it acknowledged a message.
- **Current state** comes from Firstmate's current-state read. Status-log lines are shown as history, never as the current state, and terminal output is a bounded sample, not a transcript.
- **Stale data** is labelled: if Wheelhouse cannot read Firstmate, it keeps the last view and says how old it is.
